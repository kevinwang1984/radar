05 Claude Code 删库事件之后：git 能救的比你想的少 被 Agent 删库之后，git 到底能救回多少的实测。 中文 15 分钟 cn:juejin ›
是什么一篇 09-30 的掘金实测。起点是那条事故：有开发者在 Reddit 发帖说 Claude Code 在一次「重建项目镜像」的任务里 **103 秒删掉 48,218 个文件**，连 `.git` 里的 objects / refs / logs 一起端了（帖子已删、有存档，TechRadar 报道后 09-25 被多家转载；只有当事人自述与附件验证报告，无独立取证）。删除脚本的坏点很具体：`os.walk(followlinks=False)` + `os.path.islink()` 做的防穿越保护对 **Windows junction** 无效（`islink()` 只认符号链接、对 junction 恒为 False，`isjunction()` 直到 Python 3.12 才有），于是保护只在顶层生效；最终删除 55,550 个文件、复制回 7,332 个，净损失 48,218，范围盖进 `.git`。作者随后把自己当受害者逐招实测（git 2.34.1、Linux、本地、脚本可复现）：`git restore .` 只按 HEAD 恢复，**未提交的改动与未跟踪文件（`notes.md`）直接消失**；`git stash` 不带 `-u` 只收走 tracked 的改动，而且 stash 本体也在 `.git` 里；一旦 `rm -rf .git/objects .git/refs .git/logs`，`git status` / `log` / `fsck --lost-found` / `reflog` **四个命令同一句遗言**（`fatal: not a git repository`）。他给出的方案分两层：先用 `GIT_INDEX_FILE` + `read-tree` + `add -A` + `write-tree` + `commit-tree` + `update-ref refs/snapshots/<tag>` 给工作区拍快照（**第一版把临时 index 放在工作区，被 `git add -A` 自己吸进了快照**，挪到 `.git/snap-index` 才干净），再发现快照对象仍躺在 `.git/objects`、救不了「.git 陪葬」，于是补一层仓库外的 `git bundle create ~/backup/repo-safety.bundle --all`；模拟全灭后三步恢复（`git clone <bundle> restored` → `git fetch origin '+refs/snapshots/*:refs/snapshots/*'` → `git checkout refs/snapshots/t2 -- .`），灾前灾后的 md5 清单 **diff 为空**。可靠度排序：推远程 > bundle 到仓库外 > 本地快照 > stash > 裸奔。 为什么值得你花时间你每天让 coding agent 在真实仓库里改文件（wayfinder、DSH 的 subagent），这条给的是**失事后还剩什么**的边界，以及一条 10 分钟就能挂上的保险。三件事今天就能落地：给雷达仓库与活跃项目各加一条 `git bundle` 到仓库外的任务；把「未跟踪文件不在任何恢复路径里」当成 Agent 的默认风险写进你的约定；记住那条最容易被忽略的排序——**`.git` 和工作区在同一个目录里，所以任何「从项目根往下删」的操作都同时删掉备份**。5–10 分钟读完，脚本可直接抄。 上手成本15 分钟（读实测 + 把 bundle 命令挂进计划任务） 入口https://juejin.cn/post/7691151105850998822 读详情（翻译 + 要点）→
