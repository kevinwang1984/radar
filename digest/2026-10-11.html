04 GitHub 重做 Git 存储：Push 一年 4.9 倍，串行点只剩引用更新 Agent 把 Push 推高 4.9 倍，GitHub 重做存储。 中文 1 小时 cn:juejin ›

06 Agent 观测链路：把「工具返回了」与「模型真看到」接起来 接上「工具返回了」与「模型真看到」之间的链路。 中文 1 小时 cn:juejin ›
是什么掘金 10-10（作者 hpoenixf）的一篇工程实践，回答一个很常见的排查问题：工具返回成功、后台也有结果，模型为什么还是没用上。做法分三件事。① **先统一执行入口，再统一钩子**：网页、知识库、业务查询过去各自打日志，「成功」在不同工具里含义不同（上游返回 / 已解析 / 已裁剪），现在读取型工具全部走同一个执行协调入口，由它统一协调授权、预算、调用、结果投影与回执，新增工具不必重写一遍授权与观测；知识库的检索算法仍留在检索器里，不搬进通用层。② **钩子记录变化，不只是开始与结束**：调用前分别保留 `originalArguments` 与 `effectiveArguments`（例：工具契约声明 `quarterly` 是 `Q` 的别名，规范化后两个值都留；映射只能来自工具契约，不能由通用钩子猜用户意图），变更后的参数仍要重新校验授权；调用后把「上游原始输出 / 运行时持有的结果 / 允许进入模型上下文的结果视图」分成三份——**可以收窄，但不能悄悄改值**（删内部字段是展示处理，把「暂无报价」改成 0 是创造事实），执行状态与投影状态分开记录，于是「上游读成功但投影失败」不会被误报成上游故障；失败按执行 / 结果 / 投影 / 持久化分别建模，`ToolFailure` 是扩展点而不是万能 catch。③ **追踪延伸到最终模型输入**：结果进入下一轮时可能再被裁剪或换成引用，所以调用后钩子证明不了下一轮真的收到正文；网关在形成有效 SDK 输入时留一份有界快照并与实际提交事件关联，关联靠身份传递（**产生结果的回合与携带结果的回合不是同一件事**），不靠文本相似度猜。文章给了一个教学用诊断对象：`actionId` / `externalDispatches: 1` / `executionStatus: succeeded` / `resultSelection: {offset: 0, limit: 5}` / `appearances: [{request-8, reference-only}, {request-9, full}]`。10-06 的一次受控验证里，模型两次更新研究工作笔记都被接受，但第一次更新之后的五份后续输入只剩不可用信息；沿「更新回执 → 状态投影 → 实际请求」核对，问题落在投影逻辑把披露状态降为未知且后续没恢复——**不是「模型忘了」，是更新成功后没传到后续输入**。另两条边界写得诚实：恢复时按既有回执重放而不是重跑上游（但这**不构成对外部服务的 exactly-once 保证**）；观测先检查权限与开关、只拿副本、异常不得改写实际请求，采集超限要**保留缺口**，而不是把「没记录到」当成「没发生」。**【原站核验】** `juejin.cn` 可达、全文已读；文章未给仓库或产品名，实现无法独立复核。 为什么值得你花时间① 你在 Gitea 上跑的 Agent 会撞上同一类问题：**「工具没问题」和「模型没用上」是两件事**，中间那一段没人记录；这篇把该记的最小集合列清了（参数原值 / 有效值、执行状态与投影状态、结果在哪些请求里以什么形态出现过）。② 最值钱的是那条反直觉纪律：**投影可以收窄内容，但不能改写事实**——「删字段」与「把空值写成 0」必须区分，否则你的日志会开始撒谎；这与「确定性判断交给代码」「毒标记」是同一族验收纪律。③ 排查路径可以照抄成一张表：调用前被拒 → 查参数 / 权限 / 准入；执行成功投影失败 → 查调用后处理与结果结构；投影成功但本次只带引用 → 查上下文组装与按需读取；记录被截断或来路缺失 → **先补观测证据，不要直接归因模型**。④ 测试要跨过接口连接处，文章列的四类可以直接搬：同一回执多次进入请求只记出现位置、不增执行计数；正文被换成引用后快照里没有正文但仍关联原回执；身份重复或运行不匹配时**宁可不关联**；关闭采集时不额外读正文、观察回调抛错不污染请求与回执。**今天可做**：给你 Agent 的一次读取补两个字段——`originalArguments` 与「结果在第几次请求里以什么形态出现」，下次排查能省一半时间。 上手成本1 小时（读全文 + 给工具调用补两个字段） 入口https://juejin.cn/post/7694888649712205833 读详情（翻译 + 要点）→
