01 NVIDIA OpenShell：把 Agent 的文件、网络与密钥权限放到沙箱外判 用策略管住 Agent 能读哪些文件、连哪些服务。 中文 1 小时 cn:juejin ›
是什么NVIDIA 开源的 Agent 权限沙箱（原文对照 0.1.2 文档，作者未做本地部署实测）。核心是**判断权不在被约束的一侧**：请求先由沙箱识别是哪个程序发起，再交给沙箱外的 Supervisor 核对策略，允许后才建立真正的外部连接，Agent 不能靠自己说一句「这个请求很安全」拿到访问权。凭据由 Provider 托管——Agent 环境里拿到的是占位令牌，代理在转发前才替换成真凭据，而且**「能联网」与「能带密钥」是两次独立检查**：原文的例子是把 GitHub 的占位令牌发到另一个已放行的域名，请求依然会以 `credential_endpoint_mismatch` 被拒。文件侧用 Landlock 约束，工作负载以非 root 运行、不带 Linux capabilities；文件策略默认 `best_effort`（规则应用不上就继续跑但记高严重性告警），设为 `hard_requirement` 则直接启动失败。被拦下的请求还能反向起草规则：系统根据拒绝记录生成具体到程序 / 主机 / 端口的提案，人在宿主机批准后**热加载进正在运行的沙箱、不用重启**；另有默认关闭的 Policy Advisor 让 Agent 自己提案，Policy Prover 用 SMT 求解器检查新增访问风险（GraphQL 与 MCP 规则目前报告无法检查）。装法两行 `curl -LsSf https://raw.githubusercontent.com/NVIDIA/OpenShell/main/install.sh | sh`、`openshell sandbox create --name demo`；Windows 为实验支持，需要 WSL 2 + Docker Desktop。 为什么值得你花时间你已经在用 DSH 的并行 subagent 与 wayfinder 跑长流程，「放手让它读写执行」与「不许它碰密钥」现在只能靠提示词和 AGENTS.md 这类软约束——OpenShell 给的是硬边界，而且三条设计都能直接搬：**策略在沙箱外判**（被约束方无法自我放行）、**密钥不进 Agent 环境**（占位令牌 + 代理替换）、**权限按需申请**（据拒绝记录生成具体到主机端口的提案，人批一次即可热加载）。最后一条对你做平台尤其有用：它把「Agent 想访问什么」变成一份可审阅、可对比的提案，而不是一个「允许所有操作」的开关。今天这 5 分钟最该带走的是它的两条边界，而不是功能清单。 上手成本1 小时（读策略与 Provider 两节约 15 分钟；真跑要 Linux / macOS 或 WSL2 + Docker Desktop） 入口https://juejin.cn/post/7690756305615224867 读详情（翻译 + 要点）→

06 Jev / Kev / Laya：决策模型怎么选，什么时候该微调 把「交给谁、是否相关」写成候选项让模型直接选。 中文 1 小时 cn:juejin ›
是什么一篇 2026-09-29 的掘金选型长文，把三个「决策模型」（输入状态 + 类型化问题，直接输出选择与概率，而不是自由文本）拉到一张表上对齐。三者都支持 `choice`（从候选项里选并给出概率分布）、`score`（按等级算分）、`noul`（是 / 否命题的估计概率）。差别在交付形态与底座：**Jev** 是 TypeSafe 的托管 API，训练目标是 RLCD（Reinforcement Learning for Calibrated Decisions），官方资料未给出底座与参数量；**Kev** 在 Qwen3.5 / 3.8 上加 LoRA 与 pointer head，公开 0.8B / 4B / 9B / 27B 四档（27B 基于已后训练的 Qwen3.8-27B，bf16 权重约 55 GB、加上服务缓冲约 66 GB），提供权重与训练代码、可自托管与领域微调；**Laya** 用编码器底座（ModernBERT-large 421M / mmBERT-base 322M，默认上下文预算分别 512 / 1024 tokens），作者描述其训练同样采用 RLCD，并提供领域微调工具。数字部分最该看的是「读准确率之前先读条件」：Laya 的 **0.766 是微调后 `laya-typed-decisions` 在同一任务训练划分上的成绩**（基础 `laya` 约 0.36、`laya-multilingual` 0.352，该测试多数类基线 0.461、随机基线 0.318）；Kev 的**新来源**留出测试集是 4B 0.838 / 9B 0.852 / 27B **0.896**，而 Jev 只测了开发集 **0.857**——所以「Kev-27B 接近 Jev」说的是开发集 0.848 vs 0.857，**不能**拿 Kev 的测试集去和 Jev 的开发集排名。延迟口径也不统一（Laya 英文检查点 T4 单问题 39.5 ms、multilingual 32.8 ms；Kev-4B 在 H100 新短文本 6 个问题上中位数 18.1 ms、L40S 41.5 ms）。最后一条最容易被忽略：**三家都叫 `confidence` 的字段不是同一个数**——Kev 是归一化最大概率 `(p_max − 1/K)/(1 − 1/K)`，Laya 是 `1 − H(p)/ln K`；同一组概率 {0.6, 0.2, 0.2} 算出来是 0.400 与约 0.135，把旧系统的 `confidence >= 0.8` 原样搬到另一个实现，会自动处理的样本集合直接变了。 为什么值得你花时间你的平台里到处是这类判断——工单 / 需求分流、检索结果是否相关、要不要转人工、生成内容该走哪个引擎——而现在通常是让通用 LLM 吐一段文本再解析。这条给的是把它换成**受约束的概率接口**的完整账本：接口形状（choice / score / noul）、部署取舍（托管 API vs 自托管 27B 的 66 GB）、以及评测口径（训练来源 vs 新来源，准确率 / 校准 / 阈值表现是三件事）。要带走的是那套**最小评测方案**：固定同一批原始状态与候选项，同时记录分类准确率与 Macro-F1、Brier 与 ECE、自动处理覆盖率与被接收样本的错误率、端到端 p50 / p95，然后在同一错误预算下比覆盖率——这份清单可以直接当成你接任何决策模型时的验收模板。两条注意：Jev 的底座未公开、Kev-27B 底座的后训练数据也未知，所以这不是一次控制了变量的架构实验。 上手成本1 小时（读选型表与「confidence 不是同一个数」两节；要自建评测另算） 入口https://juejin.cn/post/7690832227404300351 读详情（翻译 + 要点）→
