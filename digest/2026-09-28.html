01 cross-agent-sync（`ass`）：换 Agent 不再失忆 跨 Agent 只读搬运会话上下文的 CLI 与 MCP。 中文 15 分钟 cn:juejin ›
是什么一篇 2026-09-27 的掘金落地复盘，外加它对应的工具：npm 包 `cross-agent-sync`（CLI 命令 `ass`，当前 0.2.2，Node ≥ 18.17；读 Cursor / OpenCode 的 SQLite 需 Node ≥ 22.5），仓库 `lhbDesign/cross-agent-sync`。它要解决的问题被作者一句话点破——不是「复制粘贴总结一下」，而是**上下文所有权**：Claude 的 `.jsonl`、Codex 的会话库、Cursor 的 `state.vscdb` 各是一套私有格式，换个 Agent 或新开一个会话就等于失忆，图片还得重贴。做法是三条硬约束：**只读聚合**（读走 `O_RDONLY`、`sqlite3 -readonly`，写路径命中受保护区直接拒绝，活跃会话被追加写入时标成「无法判定」而不是恒红，`ass doctor` 报告「本次运行未改动任何源数据」）；**把「会话」与「任务」拆开**（会话是一次对话，任务是一件事，`ass task add 登录重构 claude:<id>` 把多段会话绑成一件事，换到 Codex / Cursor 后 `ass resume 登录重构`）；**交接摘要按预算可声明地缺席**（`ass brief --budget tiny|small|standard|large|full`，超预算按节降档，被裁掉的部分明确写出来并给出看全文的命令，作者特意加了一句「省略 ≠ 不重要」，免得下一个 Agent 脑补成「没有」）。决策与踩坑不走猜：`extractDecisions` 默认关闭，正式路径是 `ass context --decision/--dead-end/--constraint/--todo` 与 `session_remember`。接了 MCP 的 Agent（Claude Code / Codex / OpenCode 等）可以直接用自然语言调 `session_handoff` / `session_task_resume`；没接的就 `ass brief <引用>` 把输出贴过去。`ass last #1 --rounds 2` 能把上一个 Agent 的最后一问连同图片搬过来（图片解码落盘，路径打在输出里）。 为什么值得你花时间你的日常就是多个 Agent 并跑——headless DSH 跑雷达、Claude Code 跑 `/implement`、Gitea 上跑 wayfinder——而「换 Agent 就得重讲一遍目标 / 已做 / 待办 / 别动哪些文件」是你每周都在付的税，`npm i -g cross-agent-sync` 之后 `cd 项目 && ass` 就属于当天见效的那一类。比功能更值得抄的是它那三条工程纪律：**只读必须可自证**（不是口头承诺）、**摘要在预算内可声明地缺席**、**决策靠显式写入而不是从对话里猜**。这三条正好对应你 AGENTS.md 里那套执行边界：边界写在提示词里只能靠自觉，写进工具的运行时可判定行为里才算数。 上手成本15 分钟（安装 + `ass` / `ass doctor`；接 MCP 再约 30 分钟） 入口https://github.com/lhbDesign/cross-agent-sync 读详情（翻译 + 要点）→

是什么AgentScope 团队开源的 Python 个人 Agent 工作站（仓库 `agentscope-ai/QwenPaw`，Apache-2.0，PyPI 包 `qwenpaw`，35.3K 星；`pip install qwenpaw && qwenpaw init --defaults && qwenpaw app`，Console 在 127.0.0.1:8088，另有 Docker、桌面版与 TUI）。真正值钱的不是「又一个个人助手」，而是它把**治理层**做成了五个独立机制：内核级 **Sandbox**（macOS Seatbelt、Linux Bubblewrap / Landlock、Windows AppContainer，shell 命令跑在受限文件系统视图里）；**Tool Guard**（YAML 规则引擎 + `ShellEvasionGuardian`，在每次工具调用前检查命令注入、路径穿越、反弹 shell、混淆攻击，审批档位 STRICT / SMART / AUTO / OFF）；独立的 **File Guard**（不受 Tool Guard 影响，默认保护 `~/.qwenpaw.secret/`、`~/.ssh` 等）；**Skill Scanner**（技能激活前扫描提示词注入、硬编码密钥、数据外泄，支持 block / warn / off 与白名单）；**Access Policy**（按能力、按来源声明 allow / deny / ask，粒度到单个工具）。记忆是三层：当前工作上下文、完整逐字历史、以及基于 ReMe 的自演进个人知识库（对话与资料持续变成可读、可改、可搜、可链接的 Markdown 记忆）。上下文用「Scroll」策略——每一轮都持久化，被换出的轮次建索引按需召回，而不是摘要掉。渠道覆盖钉钉 / 飞书 / 微信 / QQ / Discord / Telegram / iMessage，另有 ACP 做跨系统编排、内置 MCP 客户端与插件市场；也有 QwenPaw-Flash 2B / 4B / 9B 本地模型，不配 key 也能跑。 为什么值得你花时间你的 AGENTS.md 通篇在管执行边界——只做当轮范围内的动作、范围外必须先问、不许顺手跑测试——而这些边界目前**全靠提示词自觉**。QwenPaw 把同一组约束落成了代码：沙箱管文件系统视野、Tool Guard 管命令、File Guard 管敏感路径、Skill Scanner 管技能来源、Access Policy 管审批。这就是你在找的「边界该写在哪一层」的参考实现，五个层次可以直接对着抄成一张职责表，用来审你的雷达脚本、wayfinder 流程和平台侧 Agent 各自缺哪一层。哪怕不部署，`pip install qwenpaw` 后把它的 Tool Guard 规则文件与 Access Policy 定义读一遍，也够这 5 分钟。 上手成本1 小时 入口https://github.com/agentscope-ai/QwenPaw 读详情（翻译 + 要点）→

05 TPU megakernel：把 92 层 MoE 焊成一个内核 把整模型前向塞进单个 TPU 内核的推理实现，已开源。 中文 15 分钟 cn:qbitai ›
是什么量子位 2026-09-26 报道的 Inferact 与 Google Cloud 联合工程成果。Inferact 是 vLLM 原班人马的创业公司（CEO Simon Mo 是 vLLM 原始维护者，联合创始人 Woosuk Kwon 是 vLLM 发起人、PagedAttention 作者，首席科学家游凯超主导 vLLM 分布式推理；今年 1 月创业，1.5 亿美元种子轮、估值 8 亿美元，a16z 与 Lightspeed 领投，真格 / 红杉 / Altimeter 跟投）。同一套 vLLM 引擎、同一个 Kimi K3，**16 块 TPU v7 Ironwood 跑到 709 token/s，16 块 GB200 是 452，快 57%**；关掉推测解码看裸速：batch=1 时 249 vs 127，batch=8 时 865 vs 636；换到 Qwen 3.8 27B、4 块芯片，1515 vs 695。蹊跷之处在于硬件规格解释不了它——TPU v7 的 HBM 带宽 7380 GB/s **低于** GB200 的 8000 GB/s，带宽更大的那块反而更慢。差距来自芯片上面那层软件：他们把推理时原本要调度的几百个独立小 kernel 合并成一个 **megakernel**，Kimi K3 的 92 层 MoE 计算逻辑从头到尾塞进一个 Pallas 程序，一次调用走完整个前向传播；边界消失后跨层权重预取变得顺理成章——第 N 层还在算 MoE 时，第 N+1 层的 attention 权重已经开始从 HBM 往片上缓存搬。TPU 的硬件特性帮了忙：每个 TensorCore 有 64 MiB 的 VMEM 片上内存，生命周期完全交给软件管理，足够同时装下当前层计算数据与下一层预取权重；Blackwell 的片上内存分散在 152 个 SM、共约 38 MiB、由硬件调度，做同类编排限制更多。副作用是编译时间从 XLA 的 30 分钟以上降到**不到 90 秒**。加速没有精度损失：greedy decoding 下 Kimi K3 在 TPU 上的 GPQA-Diamond 94.4%、GSM8K 97.2%，与 GPU 完全一致。代码已开源（`tpu-megakernels`），但目前是针对 Kimi K3 结构做的定制优化，换架构仍需重新适配。 为什么值得你花时间这是**成本与架构判断**，不是芯片八卦。它给了一个可核对的反例：带宽更大的芯片慢 57%，差距来自「内核边界」这层软件——你评估自建推理或采购推理服务时，结论是**别拿硬件规格表做选型，要拿同一引擎、同一模型下的实测吞吐和每 token 成本**。第二层是编排思路：跨层预取能成立，前提是把整个前向当成一个可编排的程序（这也是他们绕过 XLA 手写的原因），这和你给视频生成流水线消除阶段边界、让 I/O 与计算重叠是同一种优化。第三层是成本结构：加速来自推测解码（DeepSeek 的 DSpark，acceptance length 6、单步 decode 约 8.5 ms）加内核融合，两者都不改模型，属于「不动权重就能拿到的性能」。15 分钟读官方博客与开源仓库，拿到的是可引用的数字。 上手成本15 分钟（读博客与开源仓库；真跑需 TPU 资源） 入口https://www.qbitai.com/2026/09/497425.html 读详情（翻译 + 要点）→

是什么一篇 2026-09-27 的掘金落地复盘（作者「码农悟道」）。背景是一期已做完「向量 + 关键词」混合召回，二期的痛点很典型：候选只靠向量分与关键词分加权排序，能判断「内容是否相关」却判断不了「能否真正回答问题」，于是大量「语义相似但无答案」的片段排到了有效答案前面。解法是在「候选合并去重」之后、「Top-K 筛选」之前插入 Rerank 做二次语义校验——作者明确说它不是替代召回，而是受控数量候选的精细化精排。落地定下三个目标，且都给了完整代码：**可插拔**（`RerankProvider = Literal["none","http","dashscope"]`，默认 `none` 保持旧版本兼容；配置走环境变量，非法值直接抛错）；**可降级**（未配置服务、地址为空、超时、网络异常、4xx/5xx、响应非标准 JSON、结果缺失候选 / 下标重复 / 分数非法——任一情况都自动回退到原生混合排序，Rerank 是体验增强而非核心依赖）；**可观测可复现**（每次检索记录向量分、关键词分、Rerank 分、最终分，以及排序策略版本、provider、模型名，好在指标波动时区分是关键词策略、向量权重还是精排模型的问题）。几个真金白银的坑：DashScope 的 `qwen3.7-text-rerank` **不支持公共兼容地址** `dashscope.aliyuncs.com/compatible-mode/v1/reranks`，调用直接 404，必须用业务空间专属域名且请求体是 `input` / `parameters` 嵌套结构（旧版 `qwen3-rerank` 才是扁平体）；响应解析**绝不能按响应顺序赋分，必须按原始下标回填并校验覆盖全部候选**，否则分数与内容错位；403 AccessDenied 说明请求已到服务端，要核 API key / Workspace ID / 部署区域 / 模型开通权限；以及**改配置后历史评测数据不会自动刷新**，必须重启服务重新发起检索。降级处的日志还做了脱敏，只记异常类型。 为什么值得你花时间你接的是第三方生成模型（生视频 / 生图 / 改写），和这篇接第三方 Rerank 是**同一类依赖**：外部服务、协议不统一、随时会挂。这篇文章的价值不在 Rerank 本身，而在于它把「外部模型依赖」该有的三件事写全了——provider 抽象（含默认 `none` 的兼容路径）、全场景降级（异常一律回到可用老路径，且日志可归因）、按原始下标严格对齐的响应校验（下标覆盖不全就拒收）。把它搬到你的模型调用层，就是一次「新能力上线但不引入单点故障」的翻版；文末那张逐级排查清单（404 查协议与路径、403 查空间与权限、200 无分数查下标完整性、确认看的是最新数据而非缓存）可以直接当接入 checklist 用。15 分钟读完代码。 上手成本15 分钟（读代码与清单；接入需自己的检索链路） 入口https://juejin.cn/post/7689676713794551851 读详情（翻译 + 要点）→
