上下文工程：决定 Agent 跑到第 50 轮还能不能干活

用五个动作管理 Agent 每一轮该看到什么。
中文 15 分钟 cn:juejin

摘要 · 译自原文

一篇讲 agent 上下文管理的中文实操文。它的起点是一个常见困惑：同一个模型、同一份工具列表，两个 Agent 在第 10 轮时看起来差不多，到第 50 轮却可能完全不同——一个还能准确说出刚改了哪些文件、测试为什么没过、下一步做什么，另一个开始重复读文件、忘记用户约束，甚至改动已经确认过的代码。作者认为这通常不是模型智商掉了，而是上下文管理出了问题：模型能力由提供商决定，开发者真正能控制的是每一轮把什么放进上下文、什么留在外面。

文章把手段整理成五个可组合动作：Offload（信息太挤，先搬到文件或数据库）、Reduce（太长就压成摘要、占位符或更短表示）、Retrieve（不在窗口里就按需检索回来）、Isolate（一个窗口装不下就拆成多个独立上下文）、Cache（重复计算贵就复用结果）。其中 Offload 被排在第一优先级——工具执行结果是典型例子，一次 Grep 可能返回几百行、一次网页读取几万字符，Agent 当前只需要知道「在哪些文件里命中了什么」，完整内容写盘、需要时再 Read。

压缩被拆成三层递进：Microcompact 不改消息结构也不删整段对话，只把没人再用的旧工具结果替换成 `[Old tool result content cleared]`，消息还在、轮次仍可追踪；Snip 更激进，直接从历史头部删消息，内容永久丢失，所以需要状态系统标记哪些消息不能删；再往上才是摘要。另一组关键区分是「全量预填充」与「Just-in-time」：JIT 按成本递增使用工具——先 Glob 按文件名找相关文件只拿路径，再 Grep 搜关键词拿命中行，最后才 Read 读最可疑的文件。RAG 与 Agentic Search 都属于 JIT，区别在于「要不要搜」由系统在生成前决定，还是交给 Agent 在循环里动态决定。

要点

  • 五个动作：Offload / Reduce / Retrieve / Isolate / Cache，是组合拳而非五选一
  • Offload 优先：工具结果落盘，上下文里只留「日志文件在哪、下一步为什么需要它」
  • 压缩三层：Microcompact（只清旧工具结果，消息结构不变）→ Snip（从头部删消息，永久丢失）→ 摘要
  • JIT 按成本递增用工具：Glob 拿路径 → Grep 拿命中行 → Read 读可疑文件
  • RAG 与 Agentic Search 都是 JIT，区别在「要不要搜」由系统还是由 Agent 决定

为什么值得你花时间

你正在搭的 agent 要跑几十轮的长流程，这份清单给的正是「哪一层该丢什么、什么时候丢」的操作口径，连 microcompact 的替换文案和工具的成本阶梯都能直接搬进你的 harness；15 分钟读完就能给现有链路挑出一两处该 offload 的地方。
