break-ui：用最坏的真实数据把界面打穿，再让你决定改哪条

把演示数据换成最坏真实数据，逼出界面崩溃点。
其他 15 分钟（纯提示词技能，零依赖零 key；注意它两天前才首发） weekly:skills-sitemap-diff

摘要 · 译自原文

`break-ui` 是 Emil Kowalski 的 `emilkowalski/skills` 里的一条**对抗式 UI 压力测试技能**（约 2026-10-02 首发，**4.9K 安装、仓库 43.3K 星、三项安全审计全过**）。它要解决的是一个很常见的假象：界面**用演示数据看着没问题**，一换真实数据就错行、溢出、截断、挤爆。做法是把界面渲染的**每个值逐字段换成真实世界里最坏但可信的数据**——超长姓名、无法断行的邮箱、单字母名、缺失的可选字段、巨大的计数、空列表、恰好 1 条、1000+ 行、很长的翻译文案、非拉丁文字、emoji、极端数字——并把两套数据做成 **Demo data / Worst case 的 dev-only 开关**（`?data=worst` 或独立原型路由）随时切换。

工作流是 6 阶段：① 先**把组件渲染的每个值映射到它的 schema / DB / API 上限**（**查不到上限这件事本身就是一条发现**）；② 构造最坏数据集（数据必须可信或来自 schema 限制，**不许用随机乱码**）；③ 在数据边界处接开关（**开关绝不进生产**）；④ 在真实容器宽度、320px、浏览器 200% 缩放、暗色与 RTL 下逐个检查；⑤ 输出**三段式报告**——坏掉的清单（带 `file:line`）、需要你拍板的取舍、以及本来就扛住的部分；⑥ 你说 `fix all` 或 `fix 1, 3` 它才动手，改完**必须回跑演示状态防回归**。硬规则里两条最关键：**每次只改数据、不改组件与标记**，以及**绝不先修后报**。技能同时划清了边界：它只报告不重设计——重设计归 `prototype`、审美归 `emil-design-eng`、动效归 `review-animations`。

要点

  • 定位：**对抗式 UI 压力测试**，把「演示数据看着没问题」的界面用最坏真实数据打穿；只报告不重设计
  • 最坏数据集包括：超长姓名、不可断行邮箱、单字母名、缺失可选字段、巨大计数、空列表、恰好 1 条、1000+ 行、长翻译、非拉丁文字、emoji、极端数字
  • 6 阶段：**映射每个值的 schema / DB / API 上限**（查不到上限本身就是发现）→ 构造数据 → 接 dev-only 开关（`?data=worst`）→ 在 320px / 200% 缩放 / 暗色 / RTL 下检查 → 三段式报告（带 `file:line`）→ 你说 `fix all` 或 `fix 1, 3` 才修，修完回跑演示防回归
  • 硬规则：数据必须可信或来自 schema 限制、**只改数据不改组件与标记**、**开关绝不进生产**、**绝不先修后报**
  • 热度与成熟度：**Installs 4.9K、仓库 43.3K 星、Trust Hub / Socket / Snyk 三项全过**；首发仅约 2 天（≈2026-10-02），是今天唯一零依赖、零 key、真 15 分钟档的工具

为什么值得你花时间

你做的是画布 / 工作流这类**充满动态字段的界面**，而这类界面最常见的失败不是崩溃，是「演示数据一切正常、上线后遇到一个 21 字的名字就错行」。这条值 5 分钟的原因是它把「测数据边界」变成了一条可复用的动作，而且**只报告不偷改**——这正好补上你 `/code-review` 两轴复查里没有的那一维：review 看的是代码，这条看的是**界面在真实数据下的样子**。三个可直接搬的点：① **「查不到字段上限」本身就是一条要记录的发现**——你的节点参数、模型输出字段很多都没有明确上限，这条判据能把它们一个个逼出来；② **报告必须带 `file:line` 并要求你拍板**，这是一个很好的人机分工形状，可以直接搬进你自己的评审输出约定；③ **改完回跑演示状态防回归**——修「长名字」时最容易顺手把正常长度的排版弄坏，这一步就是防它的。**今天可做**：`npx skills add https://github.com/emilkowalski/skills --skill break-ui`（`github.com` 今天打不开，命令先抄下，装不上就明天试），然后对着你画布里字段最多的那个组件说一句「打破它」。
