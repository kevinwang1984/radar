Warp 如何让 Agent 自我进化

用人类评审评论自动迭代代码审查技能的闭环。
跟人 15 分钟 people:baoyu

摘要 · 译自原文

宝玉对 Claude 官方博文《How Warp builds self-improving agents on Claude》的中文解读。Warp 内部用 AI 做 code review 时发现，瓶颈不在模型能力而在没有记忆：agent 不了解项目、不知道团队规范和历史上的教训，你指出问题它下次照犯。早期补救手段——手工根据失败案例改系统提示词、完善 AGENTS.md——效果都不理想，因为它们靠人主动去做，而且团队在 PR 里写的高质量人工评论完全没被用上。

于是他们做了两个 skill 配对：一个基础 skill 负责代码审查，另一个「改进 skill」定期收集人类工程师在 PR 上对 agent 审查结果的评论，据此更新审查 skill。核心不是让模型自我评判，而是让 agent 根据人类的标注改进技能；同时把摩擦降到最低——人只要在本来就会写评论的地方写评论，收集与更新全自动。文末的 6 条实践是：写原则不写死规则（像指导聪明人一样写）、解释规则背后的为什么、让反馈零摩擦、保持 skill 精简并渐进式披露、反馈质量大于数量、「改进 skill 的 skill」可复用到其他 skill。防跑偏还有三道闸：给 agent 足够上下文做合理性检查、限制谁的反馈有权影响更新、始终保留人在循环中审核；有标准答案的领域（测试是否通过、部署是否成功）先建验证基准，没有标准答案的（代码风格、文档质量）只交给领域专家判断。

要点

  • 两个 skill：一个做代码审查，另一个收集人类 PR 评论并更新前者
  • 改进动力来自人类标注而非模型自我评判；人在原工作流里评论即可，无需额外步骤
  • 6 条实践：写原则不写死规则 / 解释为什么 / 反馈零摩擦 / skill 精简 + 渐进式披露 / 质量大于数量 / 改进 skill 可复用
  • 三道闸：限制反馈来源的权重、保留人工审核、有标准答案的领域先建验证基准
  • 作者反例：他自研的写作自我进化 skill 曾因缺少统一标准而「越写越糟」

为什么值得你花时间

你已经养着一批本地 skill 补丁，最大的风险就是没人给它们反馈、越用越旧；这套低摩擦循环可以照搬到你的 skill 库上，尤其是「谁能影响更新 + 人工审核」那道闸，正好补上裸补丁没有的保护。
