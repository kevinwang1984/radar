ARTEMIS：把「确定性判断交给代码」写进语法的真机 agent

Google 开源的真机 GUI agent 与它的双模式架构。
中文 1 小时（读这篇拆解；要跑真机需要 Android 设备与 MCP 接入，属半天以上） cn:juejin

摘要 · 译自原文

这是掘金 10-07 的源码级拆解（作者「冬奇Lab」，属「LLM 自动化测试」系列第 05 篇），对象是 Google 开源的 **ARTEMIS**——官方定位「让 AI 助手和测试套件像人一样操作真机」。它的几个卖点先说清楚：跨应用自动化、多模态定位（优先用 accessibility 树给的元素索引，不可用时降级到坐标与视觉）、**原生 MCP 集成**（让 Antigravity、Claude Code、Windsurf 这类 AI IDE 直接驱动测试设备并拿到 Logcat 与截图）、双执行档位（Flash / Pro）、以及宣称在 Google Research 的 AndroidWorld 基准上达到 **99%+** 完成率。作者特别注明：代码库明确包含 Minitap `mobile-use` 的开源项目代码，**不是从零发明的架构**，这有助于判断哪些是领域共识、哪些是 ARTEMIS 的增量。

**Flash** 是单模型反应式循环（3–5 秒/步），`agent.flash.max_turns` 默认 **0（不设上限）**。它敢这么设计的前提是上下文管理**靠单向折叠而不是截断**：早期截图替换成视觉摘要、已完成的步骤压成可检索的 chunk、chunk 继续老化成 era（只留一句话摘要 + 每步最小索引：第几步、相对会话开始的时间偏移、一句话动作描述）；模块 docstring 写的是 "fold is monotonic"——后续压缩只在已折叠区域之后追加，从不还原成详细形态，所以占用有渐进上界而不是随步数线性增长；需要旧细节时用 `search_history` / `replay_steps` 主动检索。

**Pro** 的真实拓扑不是 README 示意图那条直线，而是**带环的图**：planner → convergence → perception → operator → execution_check → validator（失败回边到 convergence）→ summarizer → convergence（继续下一轮或进入 exit_settlement）。其中 `convergence_node` 本体就是 `return {}`——一个什么都不做的**汇合点**，存在的意义是把分支逻辑收敛到一处；`execution_check_node` 把「计划偏离」设计成**建议性而非阻断性**：无条件记录 Operator 每一轮动作、收集异步的 planner 校验结果，若判定偏离则只作为下一轮提示词里的 `operator_feedback`，**不回滚已做的动作、也不强制中断**（理由是弹窗、权限请求、加载延迟导致的良性偏移不该消耗重试预算）。

全文最值钱的一处是**计划语法**：Planner 产出的 Markdown 是「**双通道文档**」——**机器通道**是 checkbox 微语法（状态字符、缩进、`[Loop]` 标签），只有 harness 代码读，用来决定终止、循环保护、何时触发校验；**语义通道**是其余自由文本，只有 LLM 读，代码永不根据文字内容做分支。在这套语法里，`verify: <期望状态>`（可修复的验收标准，失败则重开里程碑触发修复）与 `assert: <期望观测>`（测试断言，失败**原样记录为合法结果、不可修复、不触发重试**）的区分**由代码解析强制**，而不是在 prompt 里加一句「请注意区分」。

执行前还有两层 **Safety Net**：`precondition_xml.py` 的 XML 层级树校验只覆盖 tap / long_press / 输入这几类动作，核心是四路加权评分（`W_ID 0.5`、`W_TEXT 0.4`、`W_BOUNDS 0.3`、`W_COORD 0.3`，缺失信号就跳过对应权重再归一化），失败原因归入结构化分类 **shifted / occupied / disappeared**；`precondition_pixel.py` 的像素级 VLM 兜底在 XML 超时或抓取失败（`XML_BYPASSED`，且明确不重试）时接手。**恢复机制没有独立的修复 Agent**：校验失败生成 `ExecutionIncident`（带 kind / category / reason / 失败次数 / 轮次）存进 `state.open_incident`，只要未清空就每轮重新渲染进 Operator 的提示词，直到某个动作成功才闭合、并在闭合那轮给一次 "CLOSED" 通知；README 原话是 "recovery is handled by the Operator itself with no separate repair agent"。此外还有三处值得记的取舍：**定位被单独路由**给专精空间坐标的 **Gemini Robotics-ER**（配置注释直言标准 LLM 缺乏亚像素级空间坐标微调、非 ER 模型会失败），**但仓库根目录当前生效的 `config/artemis.jsonc` 已把该节点改成继承 default（本地 llama.cpp Qwen3.8）**，所以 99%+ 更可能对应推荐配置而非 clone 下来就能复现的默认表现；Explorer 分 flash / pro / ultra 三档，**「never chosen by the agent」**，由配置文件 `pro.explorer.mode` 或 CLI 参数显式指定；**Checker 是只读、零副作用的裁决者**，两个入口（`run_checkpoint_check` 刻意不给实时屏幕权限、`run_final_check` 才看最终设备状态）都把权限限制在工具表上，而不是靠 prompt 约束。对外通过 FastMCP 暴露 5 个工具：`mobile_run_task`、`mobile_manage_task`、`mobile_get_device_state`、`mobile_inspect_trace`、`mobile_diagnose`。

要点

  • 定位：Google 开源的 **ARTEMIS**，「让 AI 助手和测试套件像人一样操作真机」；代码库包含 Minitap `mobile-use` 源码
  • 双模式对应**任务复杂度双峰分布**：Flash 反应式循环 **3–5 秒/步**、`max_turns` 默认 **0**；Pro 带规划与校验的多智能体图 **15–40 秒/步**
  • 上下文机制：**单向折叠**（截图→视觉摘要；步骤→chunk；chunk→era，只留一句话摘要与最小索引），docstring 明确 "fold is monotonic"，旧细节靠 `search_history` / `replay_steps` 检索
  • Pro 的真实拓扑是**带环图**；`convergence_node` 本体是 `return {}`（纯汇合点）；计划偏离只作 `operator_feedback`，**不回滚、不中断**
  • 计划语法是**双通道文档**：checkbox 微语法（状态字符 / 缩进 / `[Loop]`）只由代码读；自由文本只由 LLM 读
  • **`verify:`（可修复验收，失败重开里程碑）与 `assert:`（不可修复断言，失败原样记录、不重试）由代码解析强制区分**，不靠 prompt
  • 两层 Safety Net：XML 四路加权（`W_ID 0.5` / `W_TEXT 0.4` / `W_BOUNDS 0.3` / `W_COORD 0.3`）失败分类 **shifted / occupied / disappeared**；像素 VLM 在 `XML_BYPASSED` 时兜底
  • **无独立修复 Agent**：未闭合的 `ExecutionIncident` 每轮重新进入 Operator 提示词，成功后给 "CLOSED"
  • 定位单独路由给 **Gemini Robotics-ER**，但**当前本地配置已改为继承 default（llama.cpp Qwen3.8）**——99%+ 对应推荐配置，不是开箱默认
  • Explorer 三档（flash / pro / ultra）**由用户显式配置，never chosen by the agent**；**Checker 只读零副作用**，靠工具表而非 prompt 限制权限
  • 对外：MCP 暴露 5 个工具（`mobile_run_task` / `mobile_manage_task` / `mobile_get_device_state` / `mobile_inspect_trace` / `mobile_diagnose`），可被 Claude Code、Antigravity 等 AI IDE 直接调用
  • 核验口径：**【原站核验】** `juejin.cn` 可达、全文已读（含代码路径、配置名与常量）

为什么值得你花时间

这是今天最像「方法」的一条，四个模式可以原样搬进你自己的 agent 链路，且每一个都不需要 Android 设备：① **确定性判断交给代码、语义判断交给模型**——把「该不该结束循环、该不该触发校验」写成被代码解析的结构化标记，比在 prompt 里加一句「请注意区分」可靠得多（你还记得 09-15 那条「CLAUDE.md 是上下文不是配置，硬规则必须落到 Hook」——这是同一个结论在计划语法上的落地）。② **`assert` / `verify` 的区分值得抄进你的验收口径**：不区分它们，系统就会把「本该报红的断言」悄悄重跑到过，失败率被人为压低。③ **恢复不派第二个 agent**——把未闭合事件留在同一个 Operator 的上下文里，省掉一整套跨 agent 交接协议；代价是提示词更复杂，这笔账值得你自己算一次。④ **裁决者零副作用**：把「会产生副作用的执行」和「不产生副作用的裁决」分成互不越界的两个角色，是结构性防护而不是约定。最后一条习惯更值钱：**读任何 agent 跑分时先问「这是哪套配置测出来的」**——它自己把这件事写在了脸上。
