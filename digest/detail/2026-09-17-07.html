基于「行为评估」准则评估智能体

把 agent 测试从看结果改成断言它的每一步动作。
中文 15 分钟 cn:juejin

摘要 · 译自原文

这篇文章解读 Google 在 9 月 9 日 Harness Engineering 文章中提出的 Behavioral Evaluation（行为评估）。切入点是一个很常见的团队困境：模型没变、业务没变，只是改了 System Prompt、调了 Tool Schema、给 Coding Agent 加了个工具，重跑 benchmark 成功率反而掉了 4 个点。端到端分数能告诉你「变差了」，但答不了「哪一步变差的」——是推理退化？工具选错？参数传错？还是代码写完根本没跑测试？

Google 的思路是把 agent 当软件来测。传统软件不会只做 system test，还会拆 unit / integration / regression；agent 也一样，除了 `assert response == expected_answer`，还要能写 `assert agent.called_tool("test_runner")`。文章给出的行为断言示例包括：用户信息不完整时是主动追问还是自己猜一个答案；改完 Build 文件有没有运行 validator；完成代码修改后有没有调用测试工具；生成文档时引用的是不是正确的仓库。作者用一个电商售后例子说明「结果对 ≠ 过程对」：用户说「耳机没发货，不想要了，帮我退掉」，Agent 回「退款申请已提交」，只看结果算 PASS，但打开 trace 会发现它查错了订单、没有确认发货状态。

文章同时点出这背后的变化：agent 越来越像一个真正的软件系统，因此这些可观察、可判断、可重复验证的执行行为应该进入测试集，并通过持续回归在每次改 prompt / 换模型时回答「改坏了什么」。

要点

  • 场景：改 Prompt / Tool Schema / 加工具后 benchmark 掉分，端到端分数无法定位原因
  • 核心断言从 `assert response == expected` 扩展到 `assert agent.called_tool("test_runner")`
  • 可断言的行为：信息不全时是否追问、改 Build 后是否跑 validator、改完代码是否跑测试、引用仓库是否正确
  • 电商售后例：只看结果是 PASS（「退款申请已提交」），打开 trace 才发现查错订单、未确认发货状态
  • 主张把行为断言接入持续回归，回答「这次改动改坏了什么」

为什么值得你花时间

你的 agent 要跑几十轮长流程，这类「答对了但过程错了」的失败在线上比答错更难查；这篇文章把「哪些行为该被断言」列成了清单，可以照着给你现有链路补 3–5 条行为回归断言——以后改 prompt 或换模型时，回归跑一遍就知道改坏了什么，而不是等业务方报障。
