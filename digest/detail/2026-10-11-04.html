GitHub 重做 Git 存储：Push 一年 4.9 倍，串行点只剩引用更新

Agent 把 Push 推高 4.9 倍，GitHub 重做存储。
中文 1 小时（读全文 + 把上周的 push / fetch / 冲突数统计出来） cn:juejin

摘要 · 译自原文

这篇文章转述的是 GitHub 官方工程文章《Building Git infrastructure for agent-scale development》（2026-10-06 发布、10-07 更新）。先给的是全站负载：从 2025 年 9 月到 2026 年 8 月，月度 Git 活动从 **2182 亿次**涨到 **4733 亿次**；Push 从每月 **6.9 亿次**涨到 **33.5 亿次**，约为原来的 **4.9 倍**；2026 年 9 月，开发者与 Agent 共创建约 **73.8 亿次提交**，GitHub Actions 运行了 **32.6 亿次**。作者提醒这是全站统计，不意味着每个仓库都同速增长；真正的变化是访问模式——人类工程师一次提交经过相对完整的思考、编码与测试，Agent 工作流是持续循环（改一点、调工具、生成检查点、写分支、再读最新状态），单个 Agent 看似不快，但十个、百个并行时就从零散请求变成持续的读写流，而一次写入往往触发一串读取（测试、扫描、审查机器人、构建流水线都会重新抓取同一批对象）。

瓶颈不在磁盘速度，而在**写入路径被副本绑死**。GitHub 介绍，旧的 Spokes 架构把同一仓库的权威数据放在多台文件服务器的本地磁盘上、默认**五份完整副本**：读密集场景下这很划算（数据离计算近、副本分摊流量、冗余提高可用性），但它同时把副本当作权威持久数据，更新 Git 引用要走涉及**法定数量确认的三阶段提交**；想靠加副本来扛读，就等于让每个新副本也参与每一次写入——协调成本与故障影响随之扩大，写入受最慢副本约束。新思路是把职责拆开：权威对象放到 Azure Blob Storage 那样的持久层，读取交给轻量计算节点与缓存，扩读能力只需增减计算节点而不是新增参与写事务的权威副本；故障恢复的性质也变了——计算节点失效更接近缓存丢失（新节点从持久层重新拉取、随访问预热），而不必重建整套权威副本；Git 对象压缩与垃圾回收这类重活搬到独立后台工作节点，不再和在线请求抢文件服务器资源。

文章认为最值得学的是**哪些事情必须串行**：一次 Push 分成接收对象、验证连通关系、安全检查、更新引用几个阶段，前几件经常可以对不同对象并行，真正需要共同认可的只有「某个引用从旧提交变到新提交」这最后一步。把这些工作全塞进一把大锁实现上最直观，却会连无关的对象存储一起阻塞；GitHub 的方向是让对象存储、连通性校验与扫描尽量并行，把协调收缩到 Git 语义真正要求一致的那一段。官方称新架构在内部基准测试中最高实现 **35 倍**写入吞吐量，但文章反复强调：这不是所有仓库都已获得 35 倍加速，也不代表普通 Push 的延迟必然缩短 35 倍；实际幅度取决于对象大小、引用热点、缓存命中、CI 扇出与请求地域。文末给的三个「今天就能量」的指标是：Push 与合并延迟的 p95 / p99（尤其多个 Agent 同推一个仓库时的排队时间）、非快进更新被拒与基线过期（区分真实内容冲突与临时资源拥堵）、单次 Push 带来的读取放大（一次提交触发多少次 fetch / 构建 / 扫描）。最容易犯的工程错误则被点名：给多个 Agent 配不同提示词却让它们共享一个工作目录、一个临时分支或一套发布凭据——表面并行、实际把最容易冲突的状态放在共享区。

要点

  • 全站负载（2025-09 → 2026-08）：月度 Git 活动 **2182 亿 → 4733 亿**；Push **6.9 亿 → 33.5 亿 / 月（约 4.9 倍）**；2026-09 单月约 **73.8 亿次提交**、Actions **32.6 亿次**运行
  • 旧架构的根因：Spokes 把仓库放在多台文件服务器本地盘、默认 **5 份完整副本**，副本既是读扩容手段又是权威数据，引用更新要走带法定数量确认的**三阶段提交**——多加一份副本就多一份写路径协调成本
  • 新方向：权威对象进 Azure Blob 持久层，读取交给轻量计算节点 + 缓存；GC / 压缩搬到独立后台工作节点；写入路径上**只有引用更新必须串行**，对象接收 / 连通性校验 / 安全扫描并行
  • 官方口径：内部基准最高 **35 倍**写入吞吐，但**不是所有仓库都提速 35 倍**，也不代表 Push 延迟同步缩短
  • 三个可立刻量的指标：Push / 合并延迟 **p95 与 p99**、**非快进被拒与基线过期**分开统计、**单次 Push 的读取放大**；以及那条纪律：网络超时 ≠ 动作没发生，恢复先只读检查远端引用

为什么值得你花时间

① 你的工作台正是「一个人 + 一堆 Agent 往同一个 Gitea 仓库推」，这篇把即将到来的瓶颈指出来了：**读可以用副本和缓存摊，写不行**，写路径上每多一个必须共同认可的参与者就多一份协调成本。② 三个不用动架构就能量的指标（原文给得很具体）：Push / 合并延迟的 **p95 与 p99**（多个 Agent 同时推时尤其要看排队时间，几百毫秒的波动人感觉不到、在循环调用里会变成很长的等待）、**非快进更新被拒与基线过期**分开统计（区分真实内容冲突与资源拥堵，只有后者才适合有边界的退避重试）、**单次 Push 触发的读取放大**（一次提交引出多少次 fetch / 构建 / 扫描，缓存与去重的收益常常大于把某个 Agent 加速几个百分点）。③ 最容易犯的错是「**Agent 并行、状态共享**」：给多个 Agent 配不同提示词却让它们操作同一个工作目录或临时分支，表面并行、实则把最容易冲突的状态放在共享区；更稳的边界是每个任务一份可辨认的工作树或隔离分支，先形成可审查的提交，再从唯一入口合并。④ 「网络超时 ≠ 动作没发生」：Push 后连接中断，恢复流程应先只读检查远端引用是否已指向预期提交，而不是立刻重推。**今天可做**：翻一周 CI 日志，把 push 数、fetch 数、非快进冲突数、人工纠错时间记成一张小表，先确认瓶颈在不在协作路径上。
