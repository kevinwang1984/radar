Scion：合并量 5 个月涨 12 倍后，Anthropic 重写了源码管理

为 Agent 规模重写的集中式版本控制。
跟人 1 小时（读设计与数字；系统本身不对外提供） people:simonwillison

摘要 · 译自原文

Anthropic 工程博客 10-13 的长文（`anthropic.com` 直连不可达，本文经 `r.jina.ai` 镜像读到全文）。起点是一组规模数字：**2026 年 5 月日均合并约 2,500 次代码变更，到 9 月已超过 30,000 次**；主分支历史**接近 100 GB**、压缩后的工作副本**超过 25 GB**；每天约 **2,500 万次 checkout**（还不含开发者环境、Agent 沙箱与研究任务），朴素拉取相当于**每天 600 PB 以上的 git 流量**。他们的结论是：写代码已不再是瓶颈，**为人类规模造的开发基础设施（源码管理、构建、CI）才是**；于是自研了 **Scion**（版本控制）与 **Antique**（代码评审面），外加代码搜索、源码管理 IAM 等，**7 个人、5 个月**完成 monorepo 从 git 的整体迁移，而同期合并量涨了 10 倍。此前他们靠「峰值几百个内部 git 镜像」硬顶，镜像越多越难运维，seed 快照离 main 越来越远。

设计原则直接反着 git 来：**客户端永远在线**（几乎所有客户端都是 Agent 与任务，不再需要完整本地副本）、**客户端 / 服务端不对称**（服务端算 blame、回答问题、做 merge/rebase，客户端只维护有界对象缓存与工作副本）、**一切经由 API**（CI 任务不必再持有本地仓库，这是自动 bisect 与 revert 流水线可行的前提）、**一切水平可扩**（没有 packfile、任何一处都不存在完整副本）、**commit / rebase / merge 都在服务端完成，且代价只与改动大小相关**（不是仓库大小）、**工作副本可选且天生稀疏**（协议围绕稀疏与「虚拟化 checkout」，文件按需物化）。数据结构的核心是「changeset」——写进 write-ahead log，存相对于第一父提交的改动文件列表 + 内容寻址的 blob 指针；blame、路径历史、提交图 skip list 等都作为「derived data」用同一套递归机制算出来，可按需 eager 或延迟计算。

落地效果：**基础设施的 CPU 与内存占用比原 git 镜像方案小 200 倍**，CI 与研究的 checkout **从分钟级降到秒级**，CI 单独省下 **25% CPU**，每层缓存命中率 **>99%**；开发侧的例子很扎眼 —— 早期手写的 git-to-Scion 摄取管线拿给内部版 Claude Mythos Preview 重写后，**内存少 20 倍、快 4 倍**，且保持了摄取顺序与数据结构的隐式不变量。文末的经验更值得记：工程师现在**审的是改动的意图而不是每一行**；大量工作其实是**告诉 Claude「不行」** —— Agent 会为满足某个模式而违反系统约束（例如有系统靠线性读 commit log 去查变更何时合入 main），对抗式评审很有效但也**偏执**，出现过 Claude 因为不信任另一内部服务而加了一堆过度防御的校验。他们还让专门的 Claude 盯每个组件的健康，叫「superfans」。Anthropic 也明确说了 Scion **不适合替代通用 git**，公开分享的是思路。

要点

  • 规模起点：日均合并 **2,500（5 月）→ 30,000+（9 月）**；主分支历史近 **100 GB**、压缩工作副本 **>25 GB**；每天约 **2,500 万次 checkout** → 朴素拉取 **>600 PB/天** git 流量
  • **7 人、5 个月**自研 Scion + Antique 并完成 monorepo 迁移，同期合并量涨 10 倍
  • 五条核心原则：客户端永远在线、客户端/服务端不对称、一切经由 API、无 packfile 且处处可水平扩、commit 在服务端且代价只与改动大小相关
  • 效果：基础设施 CPU/内存**小 200 倍**、checkout **分钟级 → 秒级**、CI 省 **25% CPU**、每层缓存命中率 **>99%**
  • 练手案例：手写摄取管线交给 Claude Mythos Preview 重写后**内存少 20 倍、快 4 倍**
  • 组织经验：工程师审「意图」而非逐行；主要工作是**告诉 Claude「不行」**；对抗式评审会**偏执**并诱发过度防御

为什么值得你花时间

① 这套数字是你未来 6–12 个月的预告片：**「写代码不再是瓶颈，为人类规模造的开发基础设施才是」** —— 你现在用 Gitea + Agent 的工作方式迟早撞同一堵墙（评审排队、CI 抢锁、checkout 变慢），早看见就能早决定哪些是「忍一忍」，哪些要换。② 四条不需要换版本控制就能搬走的做法：**客户端按需取（稀疏 / 虚拟 checkout）而不是先全量克隆**、**把「谁最后改了这行 / 两个提交什么关系」做成服务端 API，别让每个任务自备仓库**、**合并队列的全局锁在 Agent 规模下不成立 → 转向合并后与发布前测试**、**每层独立可扩且不共享故障域**（他们专门隔离 cache 与 server 的故障面，避免一个区域缓存挂掉拖垮全局）。③ 组织层面两条最诚实：**7 人 5 个月重写并迁移了一套源码管理系统**；以及**工程师的价值从写代码转成「说不」与设计取舍** —— 后者正是你现在带 Agent 时的实际手感。**今天可做**：把你 wayfinder 流程里「最慢的一次全量拉取或排队」找出来，看看能不能改成按需取或服务端查询。
