Mobilerun：把模型拆到角色级，而不是任务级

让 LLM 操作 Android 和 iOS 的开源框架。
中文 1 小时（读拆解；要跑真机需要 Android / iOS 设备与 Portal，属半天以上） cn:juejin

摘要 · 译自原文

这是「LLM 驱动的自动化测试」系列的第 06 篇（掘金 10-08，作者冬奇Lab；上一篇正是 10-08 简报里的 ARTEMIS）。对象是 **Mobilerun**——原名 DroidRun：仓库路径至今仍叫 `droidrun`，但 pip 包名、CLI 命令与文档站已经全部改成 mobilerun。它用 LLM Agent 控制 Android 与 iOS 设备，提供检查 UI 状态、理解截图、点击、滑动、输入文字、规划多步流程的移动端工具集，支持 OpenAI / Anthropic / Gemini / xAI / Ollama / DeepSeek / OpenRouter 等多家模型，有 CLI、终端 UI、Docker、Python 四种调用方式，并可接 Arize Phoenix 或 Langfuse 做链路追踪。文章把它和 ARTEMIS 放在一起对比：两者解决同一类问题，但架构哲学不同。

**最大的差异是模型拆分的粒度。** ARTEMIS 的 Flash / Pro 是**任务级**开关——一整个任务从头到尾用 Flash 或 Pro，中途不切换；Mobilerun 走**角色级**拆分：`manager`、`executor`、`fast_agent`、`app_opener`、`structured_output` 五个角色各自可以独立配置 provider、model 与采样参数。默认配置全部用同一个 Gemini 模型，但**温度按角色职责递减**——Manager 0.2（规划需要一点探索空间）、Executor 0.1（选择具体动作要更确定）、`app_opener` / `structured_output` 0.0（纯确定性任务不需要随机性）。文档给出的跨厂商示例更直观：规划交给 Claude，执行交给 GPT-4o，简单直接模式交给更轻量的 Gemini Flash-Lite。执行路径上也分两种：**Direct 模式**（`reasoning=False`）是单一模型、单一循环的 `FastAgent`——LLM 输出 XML 工具调用块，框架解析执行后把结果塞回对话历史，没有独立规划节点；**Reasoning 模式**（`reasoning=True`）拆成 `ManagerAgent`（分析状态、建计划与子目标、跟踪进度、判断完成）与 `ExecutorAgent`（只拿一个子目标、看当前 UI、选并执行一个动作、返回结果），用 llama_index 的 `Workflow`（`@step` 状态机）串成双节点轮转，而不是 LangGraph 那种带条件边的图。

几处值得单独看的工程细节：**Portal** —— Android 端靠一个自定义无障碍服务（框架用 `settings put secure` 管理它的生命周期）读取屏幕布局，规避 `UiAutomation` 连接互斥（同一时刻只允许一个）的限制；**坐标类工具默认被遮蔽** —— `click_at` / `click_area` / `long_press_at` 只有在截图坐标系与设备输入坐标系对齐（`screenshot_matches_input_coords`）且用户未显式指定 disabled 列表时才自动解禁，宁可让 Agent 只能按结构化索引点击；**视觉模式** —— `--vision` 只是把同一张截图额外塞进模型上下文，`--vision-only` 完全不提供无障碍树（用于游戏、WebView 这类没有 a11y 信息的 App），没有 ARTEMIS 那种专精空间坐标的定位模型，但 `vision_sizing.py` 在多模型同场时**取所有模型里最保守（最小）的分辨率上限**，保证 Manager 与 Executor 看到的「同一个像素点」指向同一位置；**凭据管理** —— 只把密钥的**名字**（如 `MY_PASSWORD`）暴露给模型，真实取值由框架从 `CredentialManager` 取出并填入，模型看到的是 `type_secret(secret_id, index)` 这个工具；**App Card** —— 把「某个 App 怎么用」写成 Markdown（仓库里带 Gmail 的示例：汉堡菜单进文件夹、右下角写邮件、过滤语法 `from:` / `subject:` / `is:unread`），运行时按包名注入 Manager 的系统提示词，`AppCardProvider` 有本地、远程与组合三种实现；**Macro** —— `MacroRecorder` 记录模型实际执行过的动作序列（含执行前后 UI 快照与时间戳），可用 `mobilerun replay <macro_file>` 重放，把「探索成本」与「重复执行成本」分开计价；**结构化输出** —— 不是执行过程中的中间产物，而是任务完成、拿到自然语言答案后**追加一次** `structured_predict()` 提取成 Pydantic 对象；**MCP** —— 方向与 ARTEMIS 相反，它是 MCP **客户端**，发现外部服务器的工具后伪装成与内置工具同形的注册项（懒连接，第一次真调用才连）。作者明确标注了两处考证不到：README 顶部那块 **91.4% benchmark 徽章指向仓库外的 `mobilerun.ai/benchmark`，仓库内没有评测方法论、任务集或评测脚本**；平台驱动的实现在外部依赖包 `mobilerun_core_local` 里，本仓库只能确认接口边界（`DeviceDriver` 基类 + `AndroidDriver` / `IOSDriver`）。

要点

  • 角色级拆分：`manager` / `executor` / `fast_agent` / `app_opener` / `structured_output` 五个角色各自配 provider、model、temperature
  • 默认温度按职责递减：Manager 0.2 → Executor 0.1 → app_opener / structured_output 0.0
  • 两种模式：Direct（单模型 XML 工具调用循环 `FastAgent`）/ Reasoning（Manager 规划 + Executor 执行，llama_index `Workflow` 双节点轮转）
  • 安全与精度细节：坐标工具默认遮蔽、只在坐标系对齐时解禁；多模型同场取**最保守的视觉分辨率上限**；凭据只把名字给模型
  • 成本设计：App Card 把已知 App 的操作写成文档注入提示词；Macro 录制并重放已探索过的动作序列
  • 集合动作两端一致：`click(index)` / `click_at(x,y)` / `type` / `swipe` / `open_app` / `complete` 等在 Android 与 iOS 上同形，平台差异隔离在 `mobilerun_core_local`
  • 考证边界：README 的 **91.4% benchmark 徽章在仓库内无可考证的评测方法论**；【原站核验】文章（`juejin.cn` 可达、全文已读），`github.com` 今天不可达、仓库未独立核对

为什么值得你花时间

你在权衡 agent 链路的粒度，这条给的是「**把成本控制下放到角色**」这个更细的旋钮，并能和你已经读过的三处内容接上：① **角色级 vs 任务级**——ARTEMIS 要你在任务开始前赌「值不值得上 Pro」；Mobilerun 让你决定「这个角色值不值得用更贵的模型」，粒度更细，代价是配置项与排查面变大（出问题先要判断是哪个角色的模型该调）。② **多模型同场时取最保守的视觉分辨率**这条比看上去更通用：只要链路里有多个模型看同一张图或同一个坐标系，就必须先统一缩放预算，否则「同一个像素点」指向的位置会不一样——你的画布 / 分镜链路只要有截图或坐标，就该有这条约束。③ **凭据只给名字、App Card 把已知知识写成文档、Macro 把探索与重复执行分开计价**——三个都是「不增加模型调用就把成本降下来」的做法，和今天 01 / 02 两条里「确定性的部分交给代码」是同一思路。**今天可做**：把「角色级模型配置」加进你的 agent 配置待评估清单；顺手记下那条 91.4% 的教训——**跑分徽章要能追到评测方法**。
