AX：谷歌开源的 Agent 编排器，空闲就挂起、恢复无冷启动

空闲就挂起的 K8s 风格 Agent 编排器。
中文 半天（Go 与 kubectl 加 ko，且必须先有一个能装 Agent Substrate 的 K8s 集群；只看概念与清单的话 15 分钟够） cn:infoq

摘要 · 译自原文

AX 是谷歌开源的声明式 AI Agent 编排器与运行时（`google/ax`，Apache-2.0，Go 编写，托管于 agentexecutor.io），跑在 **Agent Substrate** 之上——后者是专为「密集型 Actor 多路复用」设计的执行运行时。它要解决的是一个新形态的工作负载：Agent **既不是无状态微服务**（请求—响应、生命周期短），**也不是跑完即止的批处理**（确定性执行到完成）。Agent 有状态、突发、长跑：推理与工具执行之间夹着等模型 API、等外部反馈、等人干预的长时间空闲。传统 K8s 或容器编排在这些空闲阶段仍让专用沙箱保持活跃，利用率极低；而容器运行时的冷启动又会拖慢交互式 Agent 循环。

AX 的做法是：每个 Agent 会话作为**隔离的 Actor 沙箱**运行，有严格的 CPU 与内存边界；当 Agent 进入空闲（等推理提供方或工具调用），平台**保存执行状态检查点并挂起**它，恢复做到**亚秒级且无冷启动**，并把**数十个任务复用在同一批宿主工作进程**上。控制面提供 Kubernetes 风格的声明式原语（`ax.io/v1alpha1` API 组）：**Task** 定义执行生命周期、沙箱资源约束与基础设施引用；**Workspace** 负责执行前装配环境——声明式挂载 Git 仓库、配置 MCP server、安装技能包，或用自然语言写目标让初始化 Agent 在任务启动前装好工具链与系统依赖；**Gateway** 管理出站网络安全策略（把沙箱里的 Agent 限制在明确的主机名与端口白名单内）并把凭证注入出站请求；**Model** 统一管 LLM 提供商参数、运行时配置与存在 Kubernetes Secret 里的密钥。交互全走 Go 写的 `ax` CLI：`ax apply` 注册清单、`ax watch` 实时流式看任务阶段与状态、`ax ssh` 进沙箱调试、`ax suspend` / `ax resume` 手动控制挂起与恢复；运维侧用 `ko` 把控制面部署到 K8s、把 Redis 部署到 `ax-system` 命名空间。

**它的成熟度自己写在脸上**：README 顶部挂着警告——AX 与若干功能仍在重度开发，稳定版之前很可能引入重大破坏性变更。部署门槛包括：一个 Kubernetes 集群并已安装 Agent Substrate、Go 与 kubectl、`ko` 与一个集群可拉取的镜像仓库。InfoQ 转述 Hacker News 的讨论时提到分歧：基础设施工程师称赞它消除了 Agent 空闲等待模型 API 或人工输入时的高额云成本，但也有开发者批评「符合人体工学的工作流」的宣传，因为维护 K8s 集群、容器注册表与自定义 CRD 会带来沉重的运维开销。

要点

  • `google/ax`，**Apache-2.0**，Go，**GitHub 1.3 万星**，托管于 agentexecutor.io，跑在 `agent-substrate/substrate` 之上
  • 核心机制：Agent 会话 = 隔离 Actor 沙箱；空闲时**保存检查点并挂起**，恢复**亚秒级、无冷启动**；**数十个任务复用同一批宿主进程**
  • 四类声明式原语（`ax.io/v1alpha1`）：**Task**（生命周期 + 沙箱资源约束）、**Workspace**（预装 Git 仓库 / MCP server / 技能包，或用自然语言让初始化 Agent 装依赖）、**Gateway**（出站网络白名单 + 凭证注入）、**Model**（LLM 参数与 K8s Secret 里的密钥）
  • CLI：`ax apply` / `ax watch` / `ax ssh` / `ax suspend` / `ax resume`；部署用 `ko` 到 K8s，控制面落 `ax-system`，另有 Redis
  • 门槛与风险：**官方自标「重度开发中，稳定前会有重大破坏性变更」**；需要 K8s 集群 + Agent Substrate + Go + kubectl + ko + 镜像仓库
  • HN 上意见两极：一面认可消除空闲期云成本，一面批评维护 K8s / 容器注册表 / CRD 的运维开销配不上「人体工学」的宣传

为什么值得你花时间

你要建的是「一句话成片」这种**长跑、多工具、会中途等人**的 Agent 链路，而你的成本模型里最贵的一项恰恰是**空闲等待期间还占着的资源**。AX 最值钱的不是代码（它要 K8s，你短期未必上），而是三个**可以直接搬进你现有实现的接口判断**：① **「Agent 会话是有状态 Actor」**——一旦这么建模，挂起 / 恢复、多路复用、资源超卖就都变成自然推论，而不是打补丁；② **`Workspace` 把「环境装配」声明成清单**——Git 仓库、MCP server、技能包、依赖，全部在执行前声明式装好，这条正是你 09-29 记过的「Agent 拎包入住的开发环境」的另一种实现（今天正文 06 讲的是同一件事的另一面），两者对照着看很值；③ **`Gateway` 把出站网络白名单与凭证注入收到一处**——Agent 拿不到凭证本体、只能发出被代理过的请求，这是「凭证不进 Agent」最实用的形态。今天这 5 分钟该做的：**读它的 `docs/concepts.md` 与那份 YAML 例子**（一个 Workspace + 一个 Task 就能表达「拉起 golang/go 仓库并让 Agent 从源码构建工具链」），判断你下一代沙箱要不要抄这个「声明 Workspace + 挂起空闲 Actor」的形状。
