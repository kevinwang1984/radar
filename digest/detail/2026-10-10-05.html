Elastic 预计算上下文：输入 token 减 58%，以及「组合两种上下文反而更差」

把工单证据预计算成快照，agent 少读 58% 的 token。
中文 1 小时（读全文并对照自己的 agent 输入结构） cn:juejin

摘要 · 译自原文

Elastic 的支持团队要让 agent 回答「发生了什么、有哪些证据支持根因判断、接下来该做什么」，而证据分散在工单记录、冗长的对话流、关联的工程 issue 与评论、知识文章和相关工单里。改造前 agent 必须先发现相关索引、检查 schema、执行多次查询、协调互相矛盾的更新信息，再整合出答案；同一个工单被反复追问时，这些梳理与综合分析要重复做一遍，既烧输入 token、又加延迟，还提高生成无效查询或选错数据源的概率。他们的做法是把上下文换成两级**预计算知识指标（Knowledge Indicators，KI）**：**索引 profile KI** 由工作流读取每个支持索引的 Mapping 并抽样几篇文档生成，写清这个索引的用途、能回答哪些问题、什么时候该用、关键字段、排除项、经过验证的 join 关系、时间覆盖范围与示例 ES|QL 查询；**工单级 KI** 则为每个通过的工单生成一份证据快照，含稳定工单标识符、来源引用、标签与新鲜度元数据、故障事件阶段、假设清单（分别标已确认 / 推断 / 相互矛盾 / 未解决）、根因状态与置信度、技术处理结果、可复用的经验。

两个设计细节很关键。第一是**用确定性检查治幻觉**：生成后加代码校验（尚未确定的根因必须留空且置信度必须低、推断得出的根因不能高置信、CRM 里标记已关闭的工单要与技术问题是否解决分别评估），用于修复结构矛盾而不必再调一次模型去重新解读证据。第二是**只在有用时才生成**：工单要有下游工程证据、或者至少包含两个重要对话事件（其中有支持团队参与）才继续处理；工作流拿已存 KI 的水位标记与工单及重要对话记录的最新时间戳比较，没变化就复用，不每轮重算；语料大时优先处理近期或可能被查询的工单。检索侧配了一个检索 skill，规定精确工单号走词法检索（标识符匹配）、找相似工单 / 先例走词法加语义的混合检索、非工单实体先查索引概况再查原始数据源；skill 里明确每类 KI 的职责与优先级、字段使用指导，以及缓存未命中与 Mapping 错误的恢复步骤——没有工单 KI 就当作缓存未命中回查底层数据，而不是假定现有上下文已经完整。

评估用 20 个问题、每个问题 3 次试验，两类工作流（工单调查与事后总结、跨数据源的简短技术支持问答），回答模型与工具条件相同、只变 KI 可见性，另用独立的 LLM 评判事实准确性。结果是工单级 KI 的提升最明显：工单调查**输入 token 约减少 58%、延迟约降低 40%**，技术支持问答约减少 43% / 降低 17%，事实准确性没有统计学上显著的下降。文章自己声明数据集规模小、应视为方向性信号。最反直觉的发现是**组合策略反而更差**：同时提供索引概况与工单 KI，并不比只给工单 KI 更好——看 trace 发现 agent 能理解部分工单上下文，却缺乏组合这两类 KI 的可靠规则：它用工单级 KI 做规划，但在查询原始数据时忽略了索引概况给的字段指导，用了自己推断的 schema，导致查询失败、重试和额外的模型开销。由此得到的经验是：**上下文来源必须明确各自的职责与优先级**——agent 必须知道哪个来源为答案提供依据、哪个仅用于定位证据、什么时候必须回源验证、缓存未命中或 Mapping 错误之后该怎么走。

要点

  • 两级预计算 KI：索引 profile（用途 / 可答问题 / 关键字段 / 示例 ES|QL）负责选数据源，工单级 KI 提供单工单的证据快照
  • 工单 KI 结构：故障事件阶段、假设清单（已确认 / 推断 / 矛盾 / 未解决）、根因状态与置信度、技术处理结果、可复用经验、来源引用与新鲜度
  • 确定性检查（未定根因留空且低置信、推断不得高置信、CRM 状态与技术结论分开）替代第二次模型调用
  • 效果：工单调查输入 token **约 -58%**、延迟 **约 -40%**；技术支持问答约 -43% / -17%；事实准确性无显著下降（20 问 ×3 次，样本小、作者自认只作方向性信号）
  • **反直觉结论**：同时给索引概况与工单 KI 不比只给工单 KI 更好——缺少「谁定答案、谁只定位证据、何时回源」的规则时，组合上下文会增加查询失败与重试

为什么值得你花时间

这是一份带数字的「让 agent 少读废话」的工程账，失败案例比成功案例更值钱。① **成本主项是重复的证据搜集**——58% 的输入 token 不是靠换更便宜的模型省下来的，而是把「每次回答都要重建的关联关系」提前算成快照；你的画布 / 成片 agent 里同样有「每轮重读一遍上游产物」的开销，先找出来再谈换模型。② **组合两种都有用的上下文反而更差**，这是今天最值得抄的一条：上下文来源必须写明「谁负责定答案、谁只用来定位证据、什么时候必须回源验证、缓存未命中怎么办」，否则 agent 会拿 A 做规划、用 B 的字段去查 A，越给越乱。③ **确定性检查替代第二次模型调用**——结构约束在生成后用代码修，不重新读证据，与你读过的「确定性判断交给代码」是同一结论的第三次独立验证。**今天可做**：把你 agent 一轮输入拆成「稳定证据」与「易变状态」两栏，稳定的那栏做成预计算快照。
