Rerank 落地：把「可降级」当成第一需求

给检索链路加第三方精排的可插拔、可降级实现模板。
中文 15 分钟（读代码与清单；接入需自己的检索链路） cn:juejin

摘要 · 译自原文

这是一篇 2026-09-27 的掘金落地复盘，作者「码农悟道」，讲企业智能知识库问答系统二期新增 Rerank 重排序的完整实践。起点是一期的局限：已经做了「向量检索 + 关键词检索」的混合召回（向量擅长语义相似，关键词精准命中专有名词、制度术语、错误码），但排序阶段只靠两类分数的加权值，评判维度单一——召回只判断「内容是否相关」，无法甄别「内容能否真正回答用户问题」，于是大量「语义相似但无实际答案」的片段经常排在有效答案前面；再加上文档切片长度、关键词密度、表述方式的差异会影响混合评分的准确性，只调两类权重参数的天花板很低。二期方案是在混合召回链路之后加 Rerank：`用户问题 → 向量+关键词混合召回 → 候选合并去重 → Rerank 重排序（可选）→ 筛选 Top-K 上下文 → 大模型作答 / 无依据拒答`。作者强调 Rerank **不替代召回**，而是对受控数量的候选做精细化语义相关性二次校验，属于「锦上添花的精排优化」——这样既提升排序精准度，又严格控制外部模型调用的成本与延迟。

落地定下三个目标，每个都给了可抄的代码。**可插拔**：用 `RerankProvider = Literal["none", "http", "dashscope"]` 约束类型，配 `resolve_rerank_provider()` 做配置校验，非法值直接 `ValueError`；默认 `none` 以最大程度兼容旧逻辑，配置全部走环境变量（`RERANK_PROVIDER` / `BASE_URL` / `API_KEY` / `MODEL` / `TIMEOUT_SECONDS`，默认超时 5 秒）。**可降级**：Rerank 是体验增强而非核心必备，绝不能成为单点故障，因此只要出现「未配置 provider 或地址为空、请求超时或网络异常、返回 4xx/5xx、响应非标准 JSON 或结构异常、结果缺失候选 / 下标重复 / 分数非法」中的任意一种，就自动回退到原生混合排序；降级处的日志做了脱敏，只记异常类型（`http_<status>` 或异常类名）而不泄露敏感信息。**可观测可复现**：每次检索都埋点记录向量分、关键词分、Rerank 精排分、最终排序分，以及本次使用的排序策略版本、Rerank provider 与模型名——这样指标波动时可以精准定位是关键词策略、向量权重还是精排模型的问题，避免盲目排查。

三个高频踩坑值得单独记住。第一，**协议不统一**：通用 HTTP 服务用扁平请求体（`model` / `query` / `documents` / `top_n`，返回 `results: [{index, relevance_score}]`），但 DashScope 的 `qwen3.7-text-rerank` **不支持公共兼容地址** `dashscope.aliyuncs.com/compatible-mode/v1/reranks`，调用会直接 404，必须用业务空间专属域名 `https://{WorkspaceId}.cn-beijing.maas.aliyuncs.com/api/v1/services/rerank/text-rerank/text-rerank` 且请求体是 `input` / `parameters` 嵌套结构（旧版 `qwen3-rerank` 才是扁平体），新旧模型协议不互通。第二，**响应解析必须按原始下标回填**：Rerank 返回是按分数降序排列的，绝不能按响应顺序赋值，否则分数与内容错位；作者的 `parse_rerank_scores()` 还做了全套校验——index 必须是真整数（排除 bool）、分数必须是有限数值、不允许重复 index、且 `set(scores)` 必须覆盖 `range(candidate_count)`，最后还原成与输入候选一致的顺序返回。第三，**403 与缓存**：403 AccessDenied 说明请求已到达服务端，通常是 API key、Workspace ID、部署区域与模型开通权限不匹配，要逐项核对业务空间；而 Rerank 分数只在**新的检索请求**中生成，改完配置历史评测数据不会自动刷新，必须重启服务并重新发起检索才能看到效果。文末还给了一张逐级排查清单（先确认服务已重启无旧配置缓存 → 核对 provider / 地址 / 模型 / 超时 → 单条候选测试看 HTTP 状态码 → 404 查路径与协议适配 → 403 查业务空间与权限 → 200 无分数查响应结构与下标完整性 → 确认看的是最新数据而非历史缓存），以及标准配置模板与后续方向（召回分与 Rerank 分的加权融合、候选数量动态适配、接缓存、灰度上线与线上抽样评测）。

要点

  • 链路位置：在「候选合并去重」之后、「Top-K 筛选」之前插入 Rerank，只做受控数量候选的二次语义校验，不替代召回
  • 三个设计目标：可插拔（`Literal["none","http","dashscope"]` + 配置校验，默认 `none` 兼容旧版）、可降级（未配置 / 超时 / 4xx / 5xx / 非标准 JSON / 下标重复 / 分数非法一律回退原生混合排序）、可观测（记录向量分、关键词分、Rerank 分、最终分与策略版本、provider、模型名）
  • 协议坑：DashScope `qwen3.7-text-rerank` 不支持公共兼容地址（404），必须用 `https://{WorkspaceId}.cn-beijing.maas.aliyuncs.com/...` 专属域名且请求体为 `input` / `parameters` 嵌套结构
  • 解析铁律：**不能按响应顺序赋分**，必须按 `index` 回填并校验覆盖全部候选；拒绝 bool 型 index、非有限分数与重复下标
  • 其余坑：403 AccessDenied 查业务空间 / 密钥 / 区域 / 模型权限；改配置后历史评测数据不会自动刷新，需重启并重新发起检索；降级日志做脱敏只记异常类型

为什么值得你花时间

你接的是第三方生成模型（生视频 / 生图 / 改写），和这篇接第三方 Rerank 是**同一类依赖**：外部服务、协议不统一、随时会挂。这篇文章的价值不在 Rerank 本身，而在于它把「外部模型依赖」该有的三件事写全了——provider 抽象（含默认 `none` 的兼容路径）、全场景降级（异常一律回到可用老路径，且日志可归因）、按原始下标严格对齐的响应校验（下标覆盖不全就拒收）。把它搬到你的模型调用层，就是一次「新能力上线但不引入单点故障」的翻版；文末那张逐级排查清单（404 查协议与路径、403 查空间与权限、200 无分数查下标完整性、确认看的是最新数据而非缓存）可以直接当接入 checklist 用。15 分钟读完代码。
