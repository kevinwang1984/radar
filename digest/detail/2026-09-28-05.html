TPU megakernel：把 92 层 MoE 焊成一个内核

把整模型前向塞进单个 TPU 内核的推理实现，已开源。
中文 15 分钟（读博客与开源仓库；真跑需 TPU 资源） cn:qbitai

摘要 · 译自原文

这是量子位 2026-09-26 的报道，主角是一家叫 Inferact 的推理创业公司，成绩是：**16 块谷歌 TPU v7 跑 Kimi K3，每秒 709 个 token，比 16 块英伟达 GB200 的 452 快了 57%**。做出这个成绩的既不是造 Kimi 的月之暗面，也不是造 TPU 的谷歌。Inferact 的创始团队几乎是 vLLM 的原班人马——他们去年 11 月成立、今年 1 月出来创业，拿了 a16z 领投的 1.5 亿美元种子轮（Lightspeed 领投，真格、红杉、Altimeter 跟投），估值 8 亿美元；CEO Simon Mo 是 vLLM 项目的原始维护者（伯克利 EECS，前 Anyscale），联合创始人 Woosuk Kwon 是整个 vLLM 项目的发起人（伯克利 CS 博士，导师 Ion Stoica），也是 PagedAttention 算法的提出者，首席科学家游凯超曾获清华特等奖学金、在 vLLM 中主导分布式推理开发。这次成果来自与 Google Cloud 的一项联合工程合作，目标是让 TPU 成为 vLLM 的一流支持对象，所有优化都会回馈上游，`tpu-megakernels` 仓库是第一个公开成果。

实验设置很干净：两边都是 16 块芯片（TPU v7 Ironwood 对 GB200）、都跑 Kimi K3、都用 vLLM 推理引擎，唯一变量是芯片与底层 kernel 实现。除了上面那组 709 vs 452，关掉推测解码看裸速差距同样拉得开——batch size 为 1 时 TPU 每秒 249、GB200 只有 127（接近一倍），放大到 8 时 TPU 865、GB200 636；换到 Qwen 3.8 27B，用 4 块 TPU v7 跑出每秒 1515，同配置 GB200 只有 695，差距更大。加速里有推测解码的功劳：DeepSeek 提出的 **DSpark** 框架让小模型先快速猜出一串候选 token、大模型再批量验证，猜对的跳过、猜错的回退，Inferact 在 TPU 上把 acceptance length 做到 6（每轮猜出的 token 平均有 6 个能通过验证），单步 decode 约 8.5 毫秒。精度无损：greedy decoding 验证下，Kimi K3 在 TPU 上的 GPQA-Diamond 得 94.4%、GSM8K 得 97.2%，与 GPU 上完全一致。

真正的技术点在于：**这种差距按理说该能从硬件规格表找到解释，实际情况恰好相反**——TPU v7 的 HBM 带宽是 7380 GB/s，GB200 反而更高、达到 8000 GB/s，带宽更大的那块跑得更慢。差距来自芯片上面那层软件。Inferact 用一个叫 **megakernel** 的方案解决 TPU 上的推理效率：核心思路是把模型推理时原本要调度的几百个独立小程序合并成一个大程序，消除程序之间切换时的带宽浪费。文章把瓶颈讲得很清楚——大模型推理的速度瓶颈不在计算而在数据搬运：每生成一个 token，模型的全部权重都要从 HBM 搬进芯片内部高速缓存算一遍，下一个 token 再重搬一遍；传统做法把一次推理拆成几百个 kernel 排队执行，问题出在交接间隙里内存带宽空转（CUDA Graphs 与英伟达最新的 PDL 能缩短间隙，但 kernel 之间的边界还在）。Inferact 直接消除了边界：Kimi K3 一共有 92 层 MoE 计算，他们把这 92 层的计算逻辑从头到尾塞进**一个 Pallas 程序**，一次调用走完整个模型的前向传播；边界消失后跨层权重预取就顺理成章——第 N 层还在算 MoE 时，第 N+1 层的 attention 权重已经开始从 HBM 往片上缓存搬，计算与搬运同时进行，带宽几乎没有空转时刻。TPU 的硬件特性让这种编排格外顺畅：TPU v7 每个 TensorCore 带 64 MiB 的 VMEM 片上内存，生命周期完全交给软件管理，容量足够同时装下当前层计算数据与下一层预取权重；GPU 那边 Blackwell 的片上内存分散在 152 个 SM 里、总量约 38 MiB、由硬件自动调度，做类似跨层编排的限制更多。实现上他们绕过 XLA、用 Pallas（角色类似 CUDA）手写整个 megakernel，额外好处是编译速度从 XLA 的 30 分钟以上降到**不到 90 秒**，改完一版 kernel 一分半钟就能上机验证。局限也写明了：目前这套 megakernel 是针对 Kimi K3 的模型结构做的定制优化，换一个模型架构还需要重新适配，团队接下来会把支持扩展到更多架构。

要点

  • 16 块 TPU v7 Ironwood vs 16 块 GB200，同跑 Kimi K3、同用 vLLM：**709 vs 452 token/s（+57%）**；裸速 batch=1 为 249 vs 127，batch=8 为 865 vs 636；Qwen 3.8 27B 用 4 块芯片为 1515 vs 695
  • 带宽反例：TPU v7 HBM 7380 GB/s **低于** GB200 的 8000 GB/s，差距来自软件层（megakernel），不是硬件规格
  • megakernel：把几百个 kernel 合并为一个 Pallas 程序，Kimi K3 的 **92 层 MoE** 一次调用走完前向；边界消失后做跨层权重预取，计算与搬运重叠
  • 硬件前提：TPU v7 每个 TensorCore 有 **64 MiB 软件管理 VMEM**；Blackwell 片上内存分散 152 个 SM、约 38 MiB、硬件调度
  • 推测解码：DeepSeek 的 **DSpark**，acceptance length 6、单步 decode 约 8.5 ms；编译时间从 XLA 的 30 分钟以上降到 **不到 90 秒**
  • 精度无损：GPQA-Diamond 94.4%、GSM8K 97.2%，与 GPU 一致；代码已开源于 `tpu-megakernels`，但目前只针对 Kimi K3 结构定制

为什么值得你花时间

这是**成本与架构判断**，不是芯片八卦。它给了一个可核对的反例：带宽更大的芯片慢 57%，差距来自「内核边界」这层软件——你评估自建推理或采购推理服务时，结论是**别拿硬件规格表做选型，要拿同一引擎、同一模型下的实测吞吐和每 token 成本**。第二层是编排思路：跨层预取能成立，前提是把整个前向当成一个可编排的程序（这也是他们绕过 XLA 手写的原因），这和你给视频生成流水线消除阶段边界、让 I/O 与计算重叠是同一种优化。第三层是成本结构：加速来自推测解码（DeepSeek 的 DSpark，acceptance length 6、单步 decode 约 8.5 ms）加内核融合，两者都不改模型，属于「不动权重就能拿到的性能」。15 分钟读官方博客与开源仓库，拿到的是可引用的数字。
