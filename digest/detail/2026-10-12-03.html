Hermes Agent：会自己长技能的 Agent，附 Kanban 多 Agent 协作层

开源 Agent：把经验自动沉淀成可自改进的技能。
其他 1 小时（一行安装 + 建一个 Profile；Kanban 跑通要再花时间） weekly:github-seed

摘要 · 译自原文

Hermes Agent 是 Nous Research 做的开源 Agent（MIT，周榜第一，252,798 star），它给自己的定位是「唯一带内建学习闭环的 Agent」：跑完复杂任务后自主创建技能，技能在使用中自我改进，会主动提醒自己沉淀知识，用 FTS5 全文索引加 LLM 摘要检索自己过去的对话，并通过 Honcho 做跨会话的用户建模；技能格式兼容 `agentskills.io` 开放标准。它不绑定你的笔记本：可以跑在 5 美元的 VPS、GPU 集群或空闲时几乎不花钱的 serverless 上，支持 local / Docker / SSH / Singularity / Modal / Daytona / Vercel Sandbox 七种终端后端，后两者空闲休眠、按需唤醒。入口有两个：终端 TUI（`hermes`，多行编辑、斜杠命令补全、可中断改向）与常驻消息网关（Telegram、Discord、Slack、WhatsApp、Signal、Email 等，`cn:juejin` 的协作篇数出 23+ 平台，含微信 / 企业微信 / 飞书 / QQ / ntfy），两者共用同一套配置、会话、记忆、技能与工具。

工程结构上有三块值得单独记。**Profile** 是一个独立的 `HERMES_HOME` 目录，包含各自的 config、.env、SOUL.md、记忆、会话、技能、cron 与状态库，创建后会自动生成同名命令别名（`coder chat` 等价于 `hermes -p coder chat`），可以各自跑自己的 Gateway 与 bot token；**Delegation** 让父 Agent 派发子 Agent 处理独立任务，子 Agent 全新上下文、只通过 goal 与 context 两个字段接收信息、完成时只回传结构化摘要以控 token，默认最多 3 并发，叶子节点禁止再次委派，且 `clarify` / `memory` / `code_execution` / `send_message` 等工具对子 Agent 不可用；**Kanban** 是一个多 Agent 协作层：SQLite 任务板是唯一事实来源，任务状态机是 triage → todo（等依赖）→ ready → running → done / blocked / archived，`ready → running` 通过一条「比较并交换」式 SQL 原子认领（命中 1 行即成功、0 行即被别人抢走），崩溃与超时由 dispatcher 的 stale recovery 回收，连续失败超过重试上限自动进 blocked 等人工介入；工作目录支持 scratch、指定路径与 **git worktree** 三种模式，worker 是各 profile 的独立进程，profile 之间没有直接 IPC、全部通过任务板流转。协作篇还归纳出 6 种可复用模式：fan-out、pipeline、fan-in、long-running journal、human-in-the-loop、fleet farming，并建议 Orchestrator Profile 只保留 kanban / memory 工具、禁用 terminal / file / web / browser 等执行型工具，让编排者不变成执行者。

安装方面，Windows 原生（不需要 WSL）一行即可：`iex (irm https://hermes-agent.nousresearch.com/install.ps1)`，装到 `%LOCALAPPDATA%\hermes`；脚本会代为安装 Python 3.14、Node.js、npm、ripgrep、FFmpeg 等依赖，若系统缺 Git 会暂存一份经过校验的 Git for Windows 到 Hermes 自己的工具目录，**不替换系统 Git**。另外从 OpenClaw 迁移有 `hermes claw migrate`（支持 `--dry-run` 先预览），会导入 SOUL.md、记忆、技能、命令白名单、消息平台配置与白名单内的 API key。

要点

  • Nous Research 开源 Agent，MIT，252,798 star；内建学习闭环：自动创建 / 改进技能，FTS5 全文 + LLM 摘要做跨会话召回，兼容 agentskills.io
  • 两个入口共用一套状态：终端 TUI 与消息网关（juejin 协作篇统计 23+ 平台，含微信 / 飞书 / QQ / ntfy）
  • Profile = 独立 `HERMES_HOME`，配置 / 会话 / 技能 / 记忆 / cron 全隔离，多实例可各跑一个 Gateway
  • Kanban：SQLite 任务板 + dispatcher，CAS 原子认领、stale recovery、失败进 blocked 等人工 unblock，工作目录可选 git worktree
  • 安装：Windows 原生 `iex (irm https://hermes-agent.nousresearch.com/install.ps1)`，装到 `%LOCALAPPDATA%\hermes`，不替换系统 Git；从 OpenClaw 迁移支持 `--dry-run`

为什么值得你花时间

① 你手上正是「一个人 + 多个 Agent 往同一个 Gitea 推」，Hermes 把这件事的**状态机**直接摆出来了：任务板是唯一事实来源、认领用原子 CAS、失败进 `blocked` 等人工 unblock、代码任务可挂 `git worktree`——这套比「给每个 Agent 一句提示词然后祈祷」稳得多；它的 6 种协作模式（fan-out / pipeline / fan-in / long-running journal / human-in-the-loop / fleet farming）可以对着你 wayfinder 的流程逐条比对，缺哪种一眼能看出来。② **「技能在使用中自我改进」**是它和你现在用的技能体系最大的差别：你这边技能是落盘的静态文档，Hermes 让它跑完复杂任务后自己写、自己改；而你今天新读的 ds-bot 也承认从它借鉴了设计——值得拿一条你写得最顺的技能做一次对照（它的 `hermes claw migrate --dry-run` 可以先预览迁移，不动原数据）。③ Windows 原生安装 + MIT + 七种后端，试错成本基本就是一条命令。**今天可做**：装好后只做一件事——建一个 `coder` Profile（`hermes profile create coder --clone`），看它的记忆与技能目录长成什么样，再决定要不要把某条流水线搬过去。
