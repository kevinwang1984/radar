07 把项目本身做成 Harness：让代码库对 Agent 可读 让代码库的隐藏状态对 Agent 可寻址。 方法 1 小时 hn:stories ›
是什么游戏开发者 Kyle Kukshtel 10-10 的演讲稿整理。他的判断是「LLM 在游戏上表现差，是因为**游戏不全是代码**」——大量状态对模型不透明，而模型只能读到代码本身。核心思路是**把不可见的东西变成可寻址的**：**固定随机源**（全局唯一带种子的随机，任何非确定性调用都走它，于是状态可精确重放）、**可截图 + 图层开关**（别让 UI 挡住你要改的那一层）、**把改动前后两张截图交给 odiff（免费 CLI 图像 diff 工具）** 产出「85% 相似」这类量化值，让 Agent 每一轮都有稳定的进步基线 —— 他说直接把整张图丢给多模态模型本身是一种**上下文污染**，绿色区域里所有没打算改的东西模型也在一起思考；**单一对象类型（fat struct `Thing`）**（树和狗在代码眼里都是「网格 + 碰撞体 + 可移动」的组合，一个类型就没有歧义、序列化也只有一条路，AI 清楚地知道该在哪里改）；**Command Pattern** 把状态变更写成可序列化命令，于是可以「回放」而不用「重新操作一遍」，甚至能在文本编辑器里拼命令直接跑、**不用编译**；**数据外置**（Type / attackDamage / walkSpeed 这类静态数据不写进代码，改数据不用重新构建）；**模拟与引擎分离**（模拟做成独立 DLL / 库，引擎只是「哑」地消费它返回的状态，于是纯 C# 就能跑测试，不用起整个游戏）；**影响评估用能被读成文本的工具** —— 性能剖析用 **samply**（把 capture 输出到控制台），因为 Agent 读不了图形化 profiler。他的结论是：这样一轮 Agent 迭代在环里只需**几秒**，所以可以**对每一次改动都跑**，而不是只在大改动时跑。【原站核验】`kylekukshtel.com` 可达、全文已读。 为什么值得你花时间① 这不是游戏专用方法，而是「**怎样让一个非纯代码的项目对 Agent 可读**」的通用答案 —— 你的画布 / 工作流产品里同样有大量「不是代码」的东西（节点图、素材、品牌规范、渲染效果），这篇给了把它们变成可寻址状态的几种手段。② 三个明天就能试的具体做法：**用 odiff 做改动前后的量化 diff**（比让多模态模型直接看两张图靠谱，还便宜）、**把 profiler 输出做成文本**（Agent 才能自己评估自己的改动）、**把稳定性做成前置约束**（种子随机、存档/读档从第一天就做，而不是最后补）。③ 「**每个改动都跑一遍完整环，因为环只要几秒**」这个目标本身就能当你 Agent 流水线的验收口径：不是问「能不能自动化」，而是问「一轮要多久」。**今天可做**：拿 odiff 对一次画布 / 生成结果做改动前后的 diff，看它给的相似度数字能不能当成你的验收基线。 上手成本1 小时（读方法；odiff 与 samply 当天就能试） 入口https://kylekukshtel.com/ai-harness-engineering-game-development-claude-code 读详情（翻译 + 要点）→
08 LangChain.js 中间件：把 Agent 的横切能力变成可组合单元 用中间件接管 Agent 的生命周期与权限。 中文 1 小时 cn:juejin ›
是什么掘金 10-13 的实战长文（作者半个落月），用一组能串起来跑的 Node.js / ESM 示例讲清 LangChain.js（`langchain` + `@langchain/langgraph` + `deepagents`）的中间件。要点逐条：**执行模型**不是「一次模型请求」，而是 `beforeAgent → beforeModel → wrapModelCall → afterModel →（工具？）→ 回到 beforeModel → afterAgent`；**统计要挂在对应事件上**（模型调用数记在 `afterModel`、工具调用数记在 `wrapToolCall` 成功之后 —— 一次带工具的调用通常是「模型 2 次、工具 1 次」，两者不是同一件事）；**`wrapModelCall` 动态改系统消息**（`request.systemMessage.concat(...)`，改完必须 `return handler(request)`，忘了调用 handler 模型就不会执行）；**`beforeModel` + `canJumpTo: ["end"]` + `jumpTo` 可以在零模型调用下短路**，但注意短路会让 `afterModel` / `afterAgent` 都不执行，**所以别把资源清理挂在 `afterAgent` 上**；**中间件可以自带工具**（顶层 `tools: []`，工具由中间件的 `tools: [...]` 注入），返回 `Command` 可以一次完成「包装 ToolMessage + 更新自定义状态」；**DeepAgents 的文件系统中间件**给 Agent 一个受控工作区：`FilesystemBackend({ rootDir, virtualMode: true })` 把真实目录映射成虚拟根（模型看到 `/todo.md`，落到磁盘就是 `<rootDir>/todo.md`），`permissions` 按**声明顺序首条匹配、未匹配默认允许**执行 —— 所以精确允许必须放在兜底拒绝之前（顺序反了看起来一样、结果完全相反），而且权限要配在 `createFilesystemMiddleware` 这一层，**塞进 `FilesystemBackend` 不会报错但完全不生效**。【原站核验】`juejin.cn` 可达、全文已读。 为什么值得你花时间① 你手上的 Agent 迟早都要这四件事：**观测（调了几次模型 / 工具）、拦截（敏感内容不进模型）、动态上下文（按租户或场景补系统指令）、受控文件访问** —— 这篇把它们统一成「中间件」，而不是散落在主流程里各写一遍。② 两条最容易踩、也最贵的坑被写清了：**规则顺序 + 默认放行**（权限系统的经典陷阱，白名单必须显式配兜底拒绝）、**配置放错层不报错但静默失效** —— 后者正是「看起来配好了」和「真的生效了」之间的差距，你在验收任何 Agent 权限时都该拿这条对照。③ 短路会让后续钩子不执行这一条，直接对应你验收时的盲区：**「某个钩子没打印」不等于「它跑失败」，可能流程压根没走到那里**。**今天可做**：把你现有 Agent 的「计数 / 拦截 / 权限」各自在代码里的位置列出来，标出哪些能收进中间件。 上手成本1 小时（Node 22 + 一个兼容 OpenAI 协议的 key） 入口https://juejin.cn/post/7695952014753529892 读详情（翻译 + 要点）→
