05 Elastic 预计算上下文：输入 token 减 58%，以及「组合两种上下文反而更差」 把工单证据预计算成快照，agent 少读 58% 的 token。 中文 1 小时 cn:juejin ›
是什么Elastic 官方号在掘金译介的支持 agent 上下文改造（作者 Abhimanyu Anand，原文 Elasticsearch Labs 博客）。改动前 agent 每回答一次都要重新发现索引、查 schema、多次查询、整合互相矛盾的更新；改法是把上下文换成两级**预计算知识指标（KI）**：**索引 profile KI** 描述每个索引的用途、能回答的问题、关键字段与示例 ES|QL 查询，用来选数据源；**工单级 KI** 为每个合格工单预生成证据快照，含故障事件阶段、假设清单（已确认 / 推断 / 相互矛盾 / 未解决）、根因状态与置信度、可复用经验。防幻觉靠生成后的**确定性检查**（未定根因必须留空且低置信、推断的根因不能高置信、CRM 已关闭与技术是否解决分开评估），并且不是每个工单都生成（要有下游工程证据或至少两个重要对话事件），未变化的水位标记直接复用旧快照。评估是 20 个问题 × 3 次试验、回答模型与工具条件相同、只变 KI 可见性，另用 LLM 评判事实准确性：工单调查**输入 token 约减 58%、延迟约降 40%**，技术支持问答约减 43% / 降 17%，事实准确性没有统计学显著下降（文中自认数据集小、只作方向性信号）。一个反直觉结果：**同时给索引概况与工单 KI，并不比只给工单 KI 更好**——trace 显示 agent 用工单 KI 做规划，却在查原始数据时忽略索引概况给的 schema，导致查询失败与重试；修法是在检索 skill 里写明每类上下文的职责、优先级、字段指导与「缓存未命中 / Mapping 错误」的回退步骤。**【原站核验】** `juejin.cn` 可达、全文已读；Elastic 英文原文今天未打开，数字为该文口径。 为什么值得你花时间这是一份带数字的「让 agent 少读废话」的工程账，失败案例比成功案例更值钱。① **成本主项是重复的证据搜集**——58% 的输入 token 不是靠换更便宜的模型省下来的，而是把「每次回答都要重建的关联关系」提前算成快照；你的画布 / 成片 agent 里同样有「每轮重读一遍上游产物」的开销，先找出来再谈换模型。② **组合两种都有用的上下文反而更差**，这是今天最值得抄的一条：上下文来源必须写明「谁负责定答案、谁只用来定位证据、什么时候必须回源验证、缓存未命中怎么办」，否则 agent 会拿 A 做规划、用 B 的字段去查 A，越给越乱。③ **确定性检查替代第二次模型调用**——结构约束在生成后用代码修，不重新读证据，与你读过的「确定性判断交给代码」是同一结论的第三次独立验证。**今天可做**：把你 agent 一轮输入拆成「稳定证据」与「易变状态」两栏，稳定的那栏做成预计算快照。 上手成本1 小时（读全文并对照自己的 agent 输入结构） 入口https://juejin.cn/post/7694627741413228594 读详情（翻译 + 要点）→
06 Strata 实测：单卡 5090 跑 125B MoE，以及三个会静默损坏产物的坑 单张 5090 跑 125B MoE 的引擎与完整实测。 中文 半天 cn:juejin ›
