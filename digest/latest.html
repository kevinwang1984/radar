是什么Hugging Face 产品负责人 Victor M 的 Ava 把三块开源件拼成一个浏览器端实时语音形象：LFM3-Omni 负责语音理解与回复，Hugging Face 的 WebGPU kernels 在设备上跑推理，TalkingHead + HeadAudio 驱动头像动画与口型同步；所有推理都在本机，对话内容不发云端。 为什么值得你花时间你做视频 / 数字人 / 口播，Ava 给的是一个「不接云端推理也能实时对话」的最小参照：三块都能单独替换，先跑通浏览器里的延迟和口型，再判断哪些环节值得自建。**今天就能做**：打开 Space 用一段语音聊两分钟，重点看首字延迟、打断后的恢复、口型是否跟得上；再把 LFM3-Omni 换成你现有 ASR / TTS 试一次。边界：这是 33 likes 的 demo，不是生产 SDK；弱显卡上的 WebGPU 延迟、口型同步和长对话稳定性都要自己测；也没有公开的部署 / 计费文档。 上手成本15 分钟（打开 Space 直接聊） 入口https://huggingface.co/spaces/townbox/ava 读详情（翻译 + 要点）→
02 Weight-Space Programming：只读权重，模型能认出网络在玩哪个游戏 不跑代码，只看权重数字就能推断网络功能。 跟人 15 分钟 people:simonwillison ›
是什么Rikiya Takehi 等人的「Sparks of Weight-Space Programming」发现前沿模型能直接读一份由浮点数组成的权重文本：GPT-6 Astra 能判断一个小网络是玩 Breakout / Pong / Pac-Man / Freeway 中的哪个，还能从零写出打败 PPO 一亿步训练网络的策略网络；更激进的是它给 Qwen3.5-0.8B 改了 0.016% 的权重，把 MATH-500 从 7.9% 拉到 48.1%。Simon Willison 用 17GB 的 Qwen 3.8 27B 在本机复现：Pac-Man 46 分 12 秒、43,506 个推理 token 猜对，Pong 1 小时 4 分、Breakout 52 分，Freeway 猜错；换 Kimi K3.1 Pro 走 OpenRouter 只要 9 分 41 秒。 为什么值得你花时间你在评估「模型能不能改自己的权重」这条线：如果权重级修正真的能绕开梯度、只改万分之几的参数就修好推理循环，那它会影响你怎么做模型定制、怎么排查微调后的退化。**今天就能做**：用 `llm -f <prompt.txt>` 跑仓库里四个自包含 prompt 中的一个，先在自己熟悉的模型上看它能不能说出「这是哪个游戏」；成本只要一次长推理。边界：论文本身是 blog-post 形态，Matthew Honnibal 批评它把「无工具读权重」和「有代码改权重」混在一起，Sean Goedecke 也拆过 Qwen 那个例子；样本只有四个 10×10 小游戏，27B 本机要跑近一小时，别当成生产级「权重编辑」能力。 上手成本15 分钟（llm + OpenRouter 跑一个 prompt；本机 27B 约 1 小时） 入口https://github.com/RikiyaT/lm_understand-logs 读详情（翻译 + 要点）→
03 Palette：大纲先改，再逐页渲染成企业模板 PPT 用可编辑大纲控制版式，逐页渲染成 PPT。 跟人 1 小时 people:hf-blog ›
是什么IBM Research 的 Palette 是一个围绕 `gpt-oss-20b-palette-lora` 的对话式 PPT 生成器：先把请求和参考文档变成一份可手改的 Markdown 大纲，再由设计师角色输出每页的配色 / 字体 / 布局 JSON，程序员角色并行写 `pptxgenjs` 代码，Node + LibreOffice 渲染成 `.pptx` 和 PDF 预览；最后一道确定性几何检查器量文字重叠 / 出界，只保留确认变好的重写。 为什么值得你花时间你做画布 / 一句话成片 / 模板化内容，最值得抄的是这条「可编辑中间态 + 确定性检查器」的拆法：把审美和坐标计算分开，用户改大纲而不是重画整页；代码里还有 `[[make this a timeline]]` 这种单页指令、5 倍过采样设计师样本、以及「改参考样例比写十条禁令更管用」的数据配方。**今天就能做**：读 `pipeline.py` / `refine.py` 和 `skills/palette/SKILL.md`，把「先出可审大纲、再渲染」搬到你现有的模板链路上。边界：PresentBench 59.7 分只测了 5 个领域中的 3 个，且不考核品牌规范；20B LoRA 权重和 1 万页合成数据未公开，`config.py` 默认还指向 Qwen2.5-Coder-32B，本地跑通要 IBM RITS / watsonx 的 key。 上手成本1 小时（读代码 + 跑远程 skill；本地跑需 IBM RITS / watsonx key） 入口https://github.com/IBM/project-palette 读详情（翻译 + 要点）→
04 StateBench：长文档里跟不住状态，长上下文也救不了 测长文档里模型还能不能跟住变量状态。 跟人 1 小时 people:hf-blog ›
是什么Ai2 的 StateBench 把「状态跟踪」拆成四级：只读一次的 r-trivial、按值重赋的 aperiodic、自引用的 soluble、按引用赋值 / 交换的 general finite（periodic）。它用同一串赋值生成四个难度版本，只改变赋值类型；在四个前沿模型（Gemini 3.8 Flash、Claude Opus 5.5、GPT-6 Sol / Luna）上，r-trivial 和 aperiodic 都还行，但 soluble / general finite 随输入变长急剧下降，最长的 general finite 上准确率只剩 13% 或更低。开源预训练模型里 transformer 在 general finite 上接近随机；Gated DeltaNet / hybrid 直接训练后能外推到数万个赋值，而 transformer 即使直接训练也学不会最难的一级。 为什么值得你花时间你在给长周期 Agent 选底座，最容易把「1M 上下文」当成「能记住状态」。StateBench 给了一个可复现的反例：上下文再长，模型也可能在「谁把刀给了谁」这类链式更新上崩掉。**今天就能做**：拿你现有任务里最长的那条状态链（画布节点、分镜角色、订单 / 素材版本），按四级各造 10 条，用你的候选模型跑一遍，记录「最新值 / 链式 / 交换」三类错误；再决定要不要把状态外置成结构化存储。边界：合成赋值序列、变量数固定、不覆盖「中途出现新实体」；论文里的理论假设和 13% 都是特定设置，不等于你的业务分布。 上手成本1 小时（读 + 造一组自己的状态链） 入口https://github.com/allenai/state-bench 读详情（翻译 + 要点）→
05 Claude Cowork 负责人：别让 Claude 扮专家，也别让它给自己打分 少设角色、多用工具与对抗审查的 Agent 用法。 中文 15 分钟 cn:infoq ›
是什么InfoQ 译出的 Felix Rieseberg（Anthropic 工程经理、Claude Cowork 负责人）访谈。他的几个反直觉做法：不要再写「你是一位资深工程师」这类角色提示，模型已经是通才，角色反而限制它；先问「这个领域最优秀的人用什么工具」，然后把工具和数据给它。审查用「对抗式」：一个 Claude 做，另外五个到十个专门找错，再由另一个 Claude 判断哪些意见成立；不要让同一个对话给自己打分，尽量找外部信号。Skill 也会过时：模型更新很快，为上一代模型写的 Skill 有时删掉更好。 为什么值得你花时间你的工作流里 Skill 和子 Agent 很多，这套方法直接对应两个常见坑：角色提示让模型演戏而不是干活；自己评自己导致「绿灯但没做完」。**今天就能做**：挑一个你最近不满意的 Skill，删掉角色段、改成「先列工具再执行」；再对一个输出开 3 个找错线程 + 1 个裁判，比较它和单轮自评的差别。边界：这是访谈 / 个人实践，不是 benchmark；「十个审查者」的 token 成本不低；具体效果依赖任务和模型。 上手成本15 分钟（读 + 改一个 Skill 的提示词） 入口https://www.infoq.cn/article/xaWSKT3MlZjbuJw16Vem 读详情（翻译 + 要点）→
06 报告已经生成，为什么还不能直接分享？ 把生成文件当版本化产物管：身份、字节、分享。 中文 15 分钟 cn:juejin ›
是什么掘金作者 hpoenixf 以 ETF Agent 的报告交付为例，拆开三件常被混为一谈的事：保存的是哪一份内容（Artifact 身份 + 内容摘要 + 归属 / 任务 / 保留期）、谁可以取得它（所有者 vs 当前访问者，定向分享绑定指定人 + 指定版本）、这次操作到了哪一步（未提交 / 已提交 / 结果未知）。同名 `comparison.html` 再生成一次就是新版本，旧分享仍指向旧字节；超时后不能立刻重跑，要先按原操作身份核对；撤销分享只阻止后续访问，不追回已下载的副本。 为什么值得你花时间你做的是「生成 → 交付」的内容平台，这条正好补上生成之后那段：报告 / 图片 / 视频的版本、回执、分享权限一旦混用，就会出现「同事打开旧链接看到新内容」或「超时重跑出两份账单」。**今天就能做**：拿你现在的导出 / 分享接口，对照文中三组字段（产物身份、访问身份、操作事实）各补一项，先把「同名文件」和「同一次保存」分开。边界：这是教学化场景，不是真实用户研究；完整的多账户定向分享不在公开版里，公开代码只到「固定产物 + 只读回读」；本地文件存储的提交也不是跨数据库 / 对象存储的全局事务。 上手成本15 分钟（读 + 对照现有交付链路） 入口https://github.com/hpoenixf/open-etf-agent/tree/34124cefc6df289e08518173789210b45a716451 读详情（翻译 + 要点）→
