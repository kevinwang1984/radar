是什么掘金 10-01 的一篇协议栈梳理，把「浏览器访问一个页面」从 DNS 到物理层逐层拆开，每层都给出了具体字节数与系统调用顺序。最有用的是那张**开销账**：500 字节的 HTTP 体 + 约 300 字节头 = 800 字节；加 TLS Record 头 5 字节 + AEAD 标签 16 字节 = 821；加 TCP 头 20 = 841；加 IP 头 20 = 861；加以太网帧头 14 + FCS 4 = **879 字节——协议开销 379 字节，开销率 75%**。由此推出 MTU 分层：以太网 1500 → MSS 1460（1500 − IP 20 − TCP 20）→ TLS Record 有效载荷 1439（再减 21），并点名 **PPPoE 场景 MTU 1492 → MSS 1452，需要 PMTUD 探测**，而「**PMTUD 黑洞**（ICMP 3/4 被防火墙丢弃）」是常见性能问题。时序账也很具体：同机房首次 HTTPS 约 **30ms = DNS 5 + TCP 握手 10 + TLS 握手 10 + HTTP 往返 5**，并注明 TLS 1.3 的 0-RTT 可省到 20ms、HTTP/3 连接迁移省掉重连开销。逐跳转发的部分强调了三条不变量：**IP 头端到端不变、MAC 每跳重写、TTL 每跳递减**，中间路由器只处理到网络层（DPI 与 NAT 是例外）。 为什么值得你花时间你每天在跟上传、下载、流式返回、跨机房调用打交道，这条给的是**一个可以用来估数与吵架的账本**。三个具体收益：**带宽与成本估算**——按 75% 协议开销率算 CDN 与出网账单，比拍脑袋准；**排障顺序**——「下载慢」先分清是 DNS、握手还是往返，30ms 的分解表直接当 checklist；**设计依据**——75% 的开销率正好解释了为什么头部压缩（HPACK）与多路复用值得上，也解释了为什么你的流式接口在小块高频返回时会被头开销吃掉。它是一篇整理稿而非一手实验（作者自己标注是「synthesis 页」、数字为经验量级），所以**当教材读、别当基准引用**。 上手成本15 分钟（读「数据包大小估算」「MTU 与分片」「完整时序」三节） 入口https://juejin.cn/post/7691166815721209897 读详情（翻译 + 要点）→
